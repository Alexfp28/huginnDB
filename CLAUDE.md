- Targets PostgreSQL, MySQL, SQLite, **MongoDB**, and **Microsoft SQL Server**. Inspired by HeidiSQL but minimal-UI / keyboard-first / Monaco-everywhere.

## Hard-earned gotchas

These bit us during the first sessions. Don't repeat them.

1. **Zustand selectors must return reference-stable values.**
   Anything like `s => s.entries.filter(...)`, `s => [...a, ...b]`, or `s => allThemes(s)` returns a fresh array each call → `Object.is` always differs → infinite re-render → React caps update depth.
   **Rule**: subscribe to the raw state, derive arrays/objects with `useMemo` in the component. The store has a banner comment in `src/stores/preferences/theme.ts` reinforcing this — don't undo it. CONTRIBUTING.md also documents the rule under "Coding standards → TypeScript / React".

2. **Monaco is bundled, not CDN-loaded.**
   `src/lib/monaco/monaco-setup.ts` wires workers via Vite `?worker` imports and calls `loader.config({ monaco })`. Without this, the SQL editor and the cell editor go blank when Tauri can't reach `cdn.jsdelivr.net`. Don't reintroduce a CDN dependency; if you add a new Monaco language, add its worker here.

3. **`tauri::State<'_, T>` does NOT auto-deref into `&T` at call sites.**
   Use `state.inner()` to get `&AppState`. Every helper that takes `&AppState` (e.g. `pool_for`) is called with `state.inner()`, not `&state`.

4. **`quote_ident` is for catalog-sourced identifiers, not arbitrary user input.**
   Documented in `src-tauri/src/db/sql.rs` and in `SECURITY.md`. User input always goes through bound parameters (`$1` / `?`).

5. **`update_cell` value is `Option<String>` end-to-end.**
   The cell editor only emits text; drivers cast textual literals server-side. Don't try to push `serde_json::Value` through it — `sqlx` postgres won't encode `Value` to arbitrary column types.

6. **The MySQL `order_clause` previously had a brittle string-rewriting hack** to convert `"col"` → `` `col` ``. Now `fetch_table_data` computes `pg_or_sqlite` once and passes the right boolean to `quote_ident` from the start. Don't reintroduce the hack.

7. **DataGrid cell-mutation callbacks pass `row.original` (the full values array), NOT a row index.** The previous index-based contract corrupted data when the user had `globalFilter` active: TanStack's `row.index` is the *filtered display* index, while parents resolved the PK from `result.rows[index]` (the unfiltered backend page). The two diverge as soon as the client filter is non-trivial. Anything that needs identity (PK lookup, delete, duplicate, FK overlay anchor) reads from the values array passed to the callback. See `DataGrid.tsx` props + `TableDataTab.pkValueFromRow`.

8. **`tab_state.json` is v5 — a list of environments (plus a global origins registry, gotcha #40), and only the main window ever touches it.** See gotcha #27 for the environment layer itself; the rest of this note describes the per-connection state *inside* an environment, which is unchanged. "Workspaces" (v2, shipped 0.5.0–1.3.0) were a stand-in for real per-window instances; 1.4.0 removed them, and the environments introduced in v4 are a different axis, not a revival. A v2 blob discards every workspace except the active one on load (confirmed product decision — no merge semantics); a v1 blob (already flat) is folded, like v3, into a single unnamed environment. `prefs::get_tab_state` / `save_tab_state` / `clear_tab_state` resolve against `active_environment()` / `active_environment_mut()` — still no per-*window* scoping on the backend at all. Secondary windows opened via `open_new_window` ("New window") are ephemeral entirely on the **frontend** side: every writer early-returns unless this is the main window, so a secondary window never calls `getTabState`/`saveTabState` and therefore never touches the file. **That guard has exactly one spelling — `isMainWindow()` in `src/lib/window.ts`** (it had sixteen, including three different comparisons against `getCurrentWindow().label`, which is how it ends up missing from a new writer). If you add a new tab-state-aware command, keep that main-window-only guard — a secondary window silently reading or writing the shared blob would corrupt the main window's session. **Each environment carries main-window-owned fields beyond `connections`:** `internalLayout` (the session workspace geometry, gotcha #10) and a `launch: LaunchState` holding `activeConnections` / `selectedConnectionId` / `activeTabId` (the connections live in the main window at last close, the focused connection, and the globally-active tab — persisted on graceful close and opportunistically on connect/disconnect via `persistLaunchState`, all main-window-guarded, read back via `get/save_launch_state`, which answer for the active environment). Those three were top-level in v3; `LaunchState` itself now lives in `tab_state.rs` rather than being declared a second time in `commands/prefs.rs`. The restore sequence lives in **`useEnvironments.restoreSession`** (`src/stores/session/environments.ts`), called both by the `App.tsx` launch effect and by `switchTo` — entering an environment is the same operation whether at boot or on a switch, and duplicating it invites drift. When `reconnectOnLaunch` is on it reads `getLaunchState()` and calls `connect(id)` with no password (falling back to the keychain secret) for each still-existing, not-already-active id; failures are per-connection and never block boot. **Order is load-bearing:** reconnect first (so every reconnected connection's tabs land in `useTabs`), THEN `hydrateWorkspaceLayout()` (gotcha #10), THEN restore focus (`setSelectedConnectionId` + `useTabs.setActive`) — the focus restore runs last because `connect()` never sets `selectedConnectionId` itself (the `App.tsx` auto-select effect picks whichever pool opened first, which is nondeterministic under the parallel reconnect).

9. **Monaco swallows `Ctrl+Enter` and friends inside its focus area; a `window` keydown listener never sees them.** That's why `QueryEditorTab` binds Ctrl+Enter via `editor.addCommand(KeyMod.CtrlCmd | KeyCode.Enter, …)` inside `handleMount`, not via `window.addEventListener`. Because `addCommand` keeps its handler closure for the lifetime of the editor, the handler reads `runQueryRef.current()` rather than capturing `runQuery` directly — otherwise it would freeze to the first render's `sql` and `running` values. Same ref pattern applies to the completion provider and the CodeLens provider. **Crucially, those two providers — plus `registerCommand` — are GLOBAL to the language, not per-editor: registering them inside `handleMount` once per query tab caused N duplicate "▶ Run" lenses (and N× autocomplete entries) with N tabs open.** They now live in `src/lib/monaco/monacoSql.ts`, installed exactly once per Monaco instance (`ensureSqlProviders`, guarded on the instance) and dispatched per model via a registry each editor populates on mount (`registerSqlEditor`) and clears on unmount. `editor.addCommand` (Ctrl+Enter, Ctrl+K) IS per-editor and stays in `handleMount`.

10. **The workspace editor is a *nested* dockview synced to `useTabs`, which stays the source of truth.** `TabbedArea.tsx` hosts an inner `DockviewReact` (separate from the outer Schema/Saved/Workspace/Console dockview in `App.tsx`); each open table/query tab is a panel. The reconciler only flows **store → dockview** for add/remove (a `useEffect` on `tabs` adds missing panels, removes stale ones); the custom tab's X button and middle-click call `useTabs.close`, never `panel.api.close()`, so removal can't feed back on itself. Active-panel sync is bidirectional but idempotent (`onDidActivePanelChange` → `setActive`; an effect mirrors `activeId` → `panel.api.setActive()`, a no-op when already active). Don't add a second add/remove path or make the close affordances mutate dockview directly. Persistence (`persistedTabs.ts`) derives its per-connection snapshot from `useTabs`; **split/float geometry IS persisted** as a raw dockview `toJSON()` blob, captured only when there's >1 group. **That blob is stored ONCE per environment (`Environment.internalLayout`, exposed via `get/save_workspace_layout`, which answer for the active one), not per connection.** It was top-level in v3, before environments existed (gotcha #27). The inner dockview is a *single* instance that hosts every open connection's tabs at once, so its geometry is a session artifact, not a per-connection one — the old per-connection `ConnectionTabState.internalLayout` duplicated the same blob under every connection and made restore order-dependent (whichever connection hydrated first won). That field is now deprecated (kept only so old blobs deserialise and so `RawState::into_state` can hoist the most-recently-used legacy blob to the top level once, on first load after upgrading); the frontend never writes it. Geometry is saved (debounced) by `scheduleSaveActive` → `saveWorkspaceLayoutNow` on `onDidLayoutChange`, and restored **once at launch** by `hydrateWorkspaceLayout` (main-window-only, gated on `restoreTabsOnOpen`) — NOT inside per-connection `hydrateTabState` anymore. **`hydrateWorkspaceLayout` MUST run AFTER the launch reconnect has populated `useTabs`** (the `App.tsx` effect calls it post-`Promise.allSettled`), because the reconciler below removes any panel whose tab isn't in `useTabs`: run it against an empty tab store and the reconciler deletes the panels `fromJSON` just built, collapsing the split back to the default tabbed layout (the sandbox bug). After `fromJSON` it prunes panels for tabs that never came back (a connection that failed to reconnect). With `reconnectOnLaunch` off there are no launch tabs, so the layout is not auto-restored — layout restore rides with reconnect by design. On hydrate the blob is handed to `TabbedArea` (`setPendingInternalLayout`) and replayed with `fromJSON` **first** — `fromJSON` is the authoritative panel+geometry rebuild (it recreates panels from the params we stored at `addPanel`), so the store→dockview reconciler then runs as an idempotent convergence pass as each connection hydrates its tabs. `fromJSON` is wrapped in try/catch: on drift it falls back to the default tabbed layout (the old behaviour). The inner dockview API is exposed to `persistedTabs` via the `registerInnerDockviewApi`/`getInnerDockviewApi` singleton in `dockview.ts`, mirroring the outer one.

11. **`sqlx` rejects `try_get::<Vec<u8>>` on a MySQL `BIT` column** (its blob compatibility check accepts only BLOB/STRING/VARBINARY). See gotcha #15 for the full, current MySQL integer/`BIT` decode + write story — it supersedes this note.

12. **Double-click on a data-grid cell edits inline, not in a modal.** `DataGrid.openCellEdit` routes by column: single-column FK → `FkCombobox`; editable cell → inline `CellInput` (the shared input also used by the insert draft row, with an *expand* button that escalates to the Monaco `CellEditor`); read-only query result → the modal as a viewer. `inlineEdit` is tracked by the row's *values array* identity (gotcha #7), not a display index. The inline commit no-ops when the value is unchanged, which is what makes the blur fired during *expand* harmless. Don't route double-click straight to the modal again.

13. **Grid "zoom" is a single persisted px value: `gridPrefs.rowHeight`.** `DataGrid` derives cell height, padding and font-size from it (via inline `style`, since the values are dynamic and can't be Tailwind classes) and adjusts it on `Ctrl`+wheel (bound as a **non-passive** native listener so `preventDefault` suppresses page-zoom — a JSX `onWheel` is passive and can't). The `TableDataTab` toolbar `+`/`−` buttons nudge the same pref. It already round-trips through `prefs.json`; no backend change is needed to use it. Subscribe to it as a primitive (gotcha #1).

14. **A field that round-trips through a typed Tauri command must be declared in the Rust struct, or serde silently drops it.** `save_tab_state` deserializes its IPC payload into the strongly-typed `ConnectionTabState` (`tab_state.rs`), which has `#[serde(default)]` but no `#[serde(flatten)]` catch-all. Unknown JSON keys are discarded on deserialize, so a "frontend-only" field survives the IPC argument shape but is gone the instant the Rust struct is rebuilt — before it's written to disk. This bit the `internalLayout` work (gotcha #10): it had to be added to *both* `src/types.ts` and the Rust struct (as `Option<serde_json::Value>`, stored opaquely). Same rule for any new persisted field on a typed command boundary. The grid's browse payload (`TableQuery`/`TableScan`/`TableFilter` in `commands/query.rs`, mirrored in `src/types.ts`) is the other place this bites, and the one with no on-disk artefact to notice it by: a dropped `withCount` silently reinstates the `COUNT(*)` issue #77 moved off the render path. Four `serde_json::from_value` tests at the bottom of `commands/query.rs` pin the exact JSON the frontend sends — copy that pattern rather than trusting the two declarations to stay in step.

15. **MySQL integer/`BIT` decoding is width- and type-specific (`mysql_value` in `src-tauri/src/db/values.rs`).** sqlx maps each MySQL integer width to one Rust type and rejects a mismatched `try_get`: `TINYINT`→`i8`, `… UNSIGNED`→`u8`/`u16`/`u32`/`u64`, etc. The `contains("INT")` branch therefore tries signed widest-first then unsigned, falling back across widths before surrendering to `Value::Null` — without this, bare `TINYINT`/`SMALLINT` and any unsigned column rendered as "NULL". `BIT` is decoded via `try_get::<u64>` (sqlx special-cases `ColumnType::Bit`; `Vec<u8>` is rejected). **A MySQL `TINYINT(1)`/`BOOL`/`BOOLEAN` column is reported by sqlx as the type name `"BOOLEAN"`** (see `ColumnType::name`: `Tiny` with display width 1 → `"BOOLEAN"`; a plain `TINYINT` stays `"TINYINT"`, and the width is never in the name — so `"TINYINT(1)"` is a name sqlx never emits). Since `"BOOLEAN"` does **not** contain `"INT"`, it must be routed into the integer branch explicitly (`contains("INT") || name == "BOOLEAN"`); the old `name == "BOOL" || name == "TINYINT(1)"` guard never matched, so booleans fell through to the `String` fallback and rendered as "NULL" (issue #68, fixed 1.9.0). We decode it as the underlying integer (0/1), not a Rust `bool`, because a `TINYINT(1)` can hold any small int (2, -1, …) and forcing `bool` would lose that. On the *write* side, editing a MySQL `BIT` cell needs `SET col = CAST(? AS UNSIGNED)` — a plain textual literal `"1"` is stored as the ASCII byte `0x31`, not the integer 1; `update_cell` takes an optional `column_type` from the frontend to detect this (a `BOOLEAN`/`TINYINT` needs no such cast — a textual `"1"` casts to the integer 1 fine).

16. **The table-structure editor builds DDL in Rust, never in the component.** `StructureEditorTab.tsx` sends the desired `TableStructure` (+ the original snapshot when editing) to `preview_structure_change` / `apply_structure_change`; the pure builder in `src-tauri/src/db/ddl.rs` (`build_ddl`) diffs them and returns the ordered statements. Preview and apply call the *same* builder so what's shown is what runs. DDL can't use bound parameters for identifiers, so every user-entered name goes through `validate_ident` before quoting, and types/defaults through `validate_type`/`validate_default` (conservative allowlists) — this is the SECURITY.md "user input never reaches `quote_ident`" rule's one sanctioned exception, mediated by validation. A rename-vs-drop+add is told apart by each `ColumnDef.original_name` (the diff matches on it). SQLite changes that `ALTER TABLE` can't express (type/nullability/PK/FK) trigger the 12-step rebuild in `build_sqlite_rebuild`; `preview` flags `rebuild: true` so the UI shows a destructive confirmation. Apply runs PG in one transaction, MySQL statement-by-statement (DDL is non-transactional there), and SQLite verbatim (the rebuild manages its own `PRAGMA foreign_keys` toggles outside any tx). Structure tabs are **not** persisted (filtered out in `persistedTabs.ts`) — they're ephemeral editing sessions.

17. **MySQL `BLOB`/`TEXT` are disambiguated by content, not just the type name (`mysql_value`, gotcha #15's neighbour).** sqlx derives the column type name (`LONGTEXT` vs `LONGBLOB`, `TEXT` vs `BLOB`, …) purely from the protocol-level `ColumnFlags::BINARY` bit, which the MySQL server *sometimes* sets on genuine text columns depending on charset/collation — so a real `LONGTEXT` arrives named `LONGBLOB` and used to render as a hex dump. The flag isn't reachable through sqlx's public API. The `contains("BLOB") || contains("BINARY")` branch therefore reads the **raw bytes** via `try_get::<Vec<u8>>` and runs `String::from_utf8` itself: valid UTF-8 → text, otherwise hex. **Crucially it must NOT use `try_get::<String>` first** — `try_get` runs sqlx's *type-compatibility* gate before decoding, and `String` is incompatible with a `BINARY`-flagged column, so it returns `Err` *without ever inspecting the bytes*; a pristine UTF-8 `LONGTEXT` (e.g. a big JSON document) then always collapsed to hex (the 1.0.10 bug). `Vec<u8>` is compatible with BLOB, so reading bytes + validating ourselves decides text-vs-binary by content. Tradeoff: a true binary blob that happens to be valid UTF-8 renders as text (same as HeidiSQL). Don't revert to `try_get::<String>` or to unconditional hex.

18. **SSH tunnel local-port bind falls back to an ephemeral port on collision (`open_tunnel` in `src-tauri/src/db/ssh.rs`).** If the user pinned a fixed `local_port` and something else already holds it (e.g. another hand-opened tunnel on the same port), `TcpListener::bind` fails with `AddrInUse`; instead of breaking the connection we retry `bind(("127.0.0.1", 0))` and let the OS pick a free port. This is transparent because the pool is pointed at the **bound** port returned on `SshTunnelHandle.local_port`, not at `tunnel.local_port`. The saved profile is never rewritten — the override lives only for that tunnel's lifetime. `local_port = 0` (auto) skips the fallback since it can't collide.

19. **`WebviewWindowBuilder::new(...).build()` must be called from an `async fn` Tauri command, never a sync one.** `commands::connection::open_new_window` hit this: a sync command building a new `WebviewWindow` on Windows deadlocks — a documented WebView2 issue — and the symptom is *not* an error, it's a window that renders blank/white and Windows tags "Not Responding". Wrapping the `build()` call in `AppHandle::run_on_main_thread` looked like a fix (the hang went away) but the window still came up blank; only marking the command `async fn` actually works, per Tauri's own docs and [tauri#13963](https://github.com/tauri-apps/tauri/issues/13963). If you add another command that creates a window, make it `async fn` from the start.
20. **`huginndb-mcp` lives in its own workspace crate (`src-tauri/mcp-server/`), never as a second `[[bin]]` in the app's own `Cargo.toml`.** It used to be exactly that (`src/bin/mcp.rs`, gated behind `required-features = ["mcp"]`), which built and ran fine — until the 1.7.0 release build switched Windows bundling from MSI to NSIS (see below) and immediately broke with `failed to bundle project when getting size of ...\mcp.exe: The system cannot find the file specified`. `tauri-bundler`'s Windows bundling enumerates *every* `[[bin]]` target in the package's own `cargo metadata`, regardless of `required-features` gating, and tries to size/bundle each one — including a binary a normal `pnpm tauri:build` never compiles. This is a known, still-open upstream limitation (tauri-apps/tauri#4807, #14176), not something fixable from `tauri.conf.json` (no config exists to exclude a `[[bin]]` from bundling). The fix is structural: move the extra binary to a sibling workspace package. Since `huginndb-mcp` was already a thin shim over `huginndb_lib::mcp::serve()` (the real logic lives in the lib crate's `mcp` module, still gated behind the `mcp` feature), the split was just a new `Cargo.toml` + `main.rs` in `mcp-server/`, a `[workspace] members = ["mcp-server"]` in the app's `Cargo.toml`, and deleting the old `[[bin]]` block — no logic moved. `cargo metadata` for the `huginndb` package alone now reports exactly one bin target, so tauri-bundler never sees the MCP binary at all. Build it with `cargo build -p huginndb-mcp --release` from `src-tauri/` (not `--features mcp --bin huginndb-mcp` anymore — that flag still *works* since the feature still gates the lib-crate logic, but the binary target it used to select no longer exists in this package).
21. **Windows installer target is NSIS, not MSI/WiX — don't switch it back without a real reason.** 1.7.0's release build reliably failed bundling the `.msi`: WiX v3 (what `tauri-action` shells out to for MSI) has been archived/unmaintained since February 2025, and its `light.exe` reliably failed to even launch on GitHub's Windows runners — a bare `failed to run ...light.exe`, no WiX diagnostic — regardless of runner OS generation (reproduced identically on both `windows-2022` and the newer `windows-latest`/Server 2025 image GitHub migrated to in June 2026) and regardless of a Windows Defender exclusion or installing the VBSCRIPT optional feature (both ran clean, neither changed the outcome). `candle.exe` always ran fine against the same freshly-downloaded WiX binaries; only `light.exe` failed, matching the historically-known pattern of Defender/AV heuristics flagging that specific binary across the Actions fleet (tauri-apps/tauri#2486, #2640, #10649) — a signature-side issue outside the repo's control, and one WiX v3 will never receive a fix for. `tauri.conf.json`'s `bundle.targets` is `["nsis", "deb", "appimage"]`. Tauri officially supports MSI → NSIS as an update path (not the reverse): the auto-updater's `latest.json` doesn't care about installer format, and NSIS detects a prior WiX MSI install and handles it (a `tauri-bundler` v1.3.0+ capability; the pinned `@tauri-apps/cli` here is 2.11.1, well past it).
22. **`huginndb-mcp` ships as a Tauri sidecar (`bundle.externalBin`), staged by the release workflow, not built by `pnpm tauri:build` itself.** Before 1.7.0 shipped, the connector was reachable only by cloning the repo and running `cargo build -p huginndb-mcp` yourself — no packaged install ever contained the binary, which defeated the point for anyone who wasn't already a contributor. The release workflow has a step (`Build and stage the huginndb-mcp sidecar`) that builds the `mcp-server` crate and copies it to `src-tauri/binaries/huginndb-mcp-<target-triple>[.exe]` — the exact naming Tauri's `externalBin` convention requires — *before* the `tauri-action` build step, so `tauri-bundler` finds it and ships it next to the main executable. `src-tauri/binaries/` is gitignored (build output, not source). **`tauri-build` (`huginndb`'s `build.rs`) hard-fails *any* compile of `huginndb_lib` — even a bare `cargo check`, even just as a dependency of `huginndb-mcp` itself — if the externalBin resource for the current target triple isn't already on disk** (existence only; content doesn't matter at compile time). That's a real circular dependency once `externalBin` is configured: building `huginndb-mcp` requires compiling `huginndb_lib` (with the `mcp` feature) first, and that compile now refuses to proceed without a sidecar file that only building `huginndb-mcp` produces. The workflow step works around it by `touch`-ing empty placeholders at both possible sidecar paths (with/without `.exe`) *before* `cargo build -p huginndb-mcp`, then `rm -f`-ing and `cp`-ing the real binary over — not overwriting the placeholder in place, since `cp` onto an existing file keeps that file's (non-executable) mode, which would silently ship a broken sidecar. If you touch this step, keep both halves. `commands::mcp::get_mcp_connector_info` resolves the *installed* sidecar's path via `std::env::current_exe()`'s parent directory — confirmed by inspecting a real `.deb` build (`dpkg-deb -c`), which places both `huginndb` and `huginndb-mcp` in the same `usr/bin/`; this is why the command doesn't need `tauri-plugin-shell` (that's for *spawning* a sidecar from within the app, which we don't do — an external AI client spawns it, we just need to tell the user where it is). Settings → MCP (`McpSection.tsx`) is the UI: it shows this path, lets the user pick which saved profiles to expose, and generates the `claude mcp add` / JSON snippet — see `docs/MCP.md`.
23. **A running `huginndb-mcp.exe` blocks the in-app self-updater from overwriting the sidecar, and the failure looks like a permissions error.** `installMode` for the NSIS bundle is left at Tauri's default (`currentUser`, writing under `%LOCALAPPDATA%`) — no admin prompt is expected, and none is needed for a plain per-user install/update. But Tauri's generated NSIS template only knows how to close a running instance of the *main* `huginndb.exe` before overwriting it; it has no idea `huginndb-mcp.exe` exists, since that process is spawned independently by whatever external MCP client has it configured (Claude Desktop, Claude Code, ...), never by HuginnDB itself. If a client still has the sidecar running when `useUpdateStore.installAndRelaunch` (`src/stores/update.ts`) downloads and silently runs the new installer, Windows holds a lock on `huginndb-mcp.exe` and the overwrite fails with `ERROR_SHARING_VIOLATION` — surfaced to the user as a generic access-denied/permissions failure, even though no elevation is actually missing. Fixed via a `NSIS_HOOK_PREINSTALL` installer hook (`src-tauri/windows/hooks.nsi`, wired through `bundle.windows.nsis.installerHooks` in `tauri.conf.json`) that force-kills `huginndb-mcp.exe` before any files are copied; the MCP client simply respawns it next time it needs the connector. Don't remove the hook, and if the sidecar's binary name ever changes, update the `taskkill /IM` target to match.
24. **The updater only ever checked on launch, so an instance that's never closed never sees a published release.** `useUpdateStore.checkOnLaunch` used to be the sole trigger — fine for a normal restart cadence, useless for a machine that leaves HuginnDB open for days. `startPeriodicChecks` (called once from `App.tsx` alongside `checkOnLaunch`) re-runs the same check on a `setInterval` (4h, module-level timer guarded against double-start so a StrictMode double-effect can't stack two). The important constraint this introduced: `install()` (the step that overwrites files, force-kills the MCP sidecar per gotcha #23, and can prompt for Windows elevation) must **never** run unattended — only `download()` is safe to run silently in the background. So `runCheck`, on finding an update, immediately kicks off `startBackgroundDownload` (a *download-only* call), which lands the store in a new `readyToRestart` status once the bytes are in; `installAndRelaunch` only calls `install()` + `relaunch()` when the user explicitly clicks (whether that's a fresh "Install" click that also happens to start the download, or a "Restart now" click against an already-downloaded update — same code path, gated on `_downloadPromise`/status so neither `download()` nor `install()` ever double-fires against the same `Update` instance). One more wrinkle worth knowing: `install()` must be called on the *exact* `Update` object that `download()` ran on — the plugin tracks the downloaded bytes on that instance internally — so `runCheck` deliberately does **not** replace `_update` with a fresh instance from a later poll when it's still the same version already mid-download or sitting at `readyToRestart`; it only replaces `_update` when a genuinely newer version appears. Because `install()` force-kills the MCP sidecar, `installAndRelaunch` also calls the new `is_mcp_sidecar_running` command (`commands::mcp`, a `tasklist`/`pgrep` shell-out — no new crate) first and, if positive, confirms with the user via `window.confirm` before proceeding (this one is intentionally *not* gated behind the `confirmDestructive` preference, same reasoning as the DROP TABLE dialog in `lib/confirmDestructive.ts` — interrupting someone else's live AI session is a different safety tier than a local data-loss confirmation).
25. **A frontend `listen(event)` with no `target` receives *every* window's `emit_to`, not just its own.** Command handlers emit Console log entries with `log_bus::emit` → `app.emit_to(window_label, …)`, targeting the window that ran the statement. But Tauri delivers an event to a listener whenever the listener's registered target is `EventTarget::Any` **or** matches the emit target (`manager::emit_filter` short-circuits on `*candidate == EventTarget::Any`), and the JS `listen(event, handler)` defaults to `{ kind: 'Any' }`. So with a second ("New window") window open, both Consoles received both windows' SQL/connection entries — the #50 duplication. Fix: `startLogBridge` (`src/lib/bridges/log-bridge.ts`) passes `{ target: getCurrentWindow().label }`, scoping the listener to `emit_to(thisLabel)` only. Global `emit` broadcasts (`log_bus::broadcast`, e.g. the keepalive connection-lost log in `keepalive.rs`) still arrive — Tauri sends an unfiltered `emit` to every listener regardless of target, which is the intended "all windows sharing the connection care" behaviour. Don't drop the `target` when adding new per-window event subscriptions; a bare `listen` re-introduces the cross-window leak.

26. **The canary channel isolates on-disk state but shares the keychain — and the state-dir name has ONE source of truth (`src-tauri/src/app_identity.rs`).** The canary build (Cargo feature `canary` + `tauri.canary.conf.json`, workflow `.github/workflows/canary.yml`, docs `docs/CANARY.md`) exists so a maintainer can dogfood a pre-release against production profiles without cutting a release. It's a *separate app*: distinct bundle identifier (`io.huginndb.canary`), product name, and its own rolling updater feed (the `canary` GitHub release's `latest.json`), installable side-by-side with stable. The one thing that makes it safe is that `crate::app_identity::APP_DIR` flips to `"HuginnDB-Canary"` under `#[cfg(feature = "canary")]`, so every state file lands in a separate config dir and a destructive one-way migration (e.g. tab-state v2→v3, gotcha #8) can't corrupt the stable install. **`APP_DIR` used to be aliased into all six state modules, which was six chances to get it wrong; the five JSON state files now resolve their paths through `state_file::path` (gotcha #41), so `APP_DIR` has exactly four consumers left: `state_file.rs`, `bridge/mod.rs`'s discovery file, `mcp/mod.rs`'s audit log, and `commands/app.rs` (which just reports the directory to the UI). Do NOT re-hardcode `"HuginnDB"` anywhere — a new JSON state file goes through `state_file`, and anything else takes `crate::app_identity::APP_DIR`, or the canary isolation silently breaks for that file.** Conversely, the keychain service (`keychain::SERVICE`) is deliberately **NOT** build-aware: canary shares `io.huginndb.app` so it reuses production passwords without the user re-entering them (isolating state but sharing credentials is the whole point — test real profiles, protect real state). The canary version is stamped `<base>-canary.<run_number>` by the workflow (prerelease suffix → always sorts below the equivalent stable version, so a canary never outranks a real release). The bundled MCP sidecar is built *stable*, not canary (its only `APP_DIR` use is the audit log; not worth a feature passthrough in the `mcp-server` crate) — noted in `docs/CANARY.md`. When editing `tauri.canary.conf.json`, remember Tauri's config merge **replaces arrays wholesale** (doesn't element-merge), which is why the overlay repeats the full `app.windows[0]` object rather than just the changed `title`.
27. **An "environment" scopes session state, not connections — and switching one has a load-bearing order.** `tab_state.json` (v4 introduced this; v5 is current — see gotcha #40) holds a list of `Environment`s (`tab_state.rs`) plus `activeEnvironmentId`; each owns a `connections` map, an `internalLayout` and a `launch: LaunchState`. Every session-state command (`get/save_tab_state`, `get/save_workspace_layout`, `get/save_launch_state`) resolves against the active one, so their signatures never changed — which is why the frontend kept working across the schema bump. **This is deliberately NOT a revival of the v2 workspaces 1.4.0 deleted:** those stood in for real per-window instances, whereas an environment is an identity (which connections are in play, and where they came from). Say so in review if someone calls it a regression.
    - **Connections are *not* owned by an environment.** `profiles.json` stays one global list; the environment tags which subset is in play. Deleting one discards tabs and geometry only — never a profile or a keychain entry. Conversely, deleting a *profile* sweeps **every** environment's `connections` and `launch` lists (`clear_tab_state` + `commands::connection::delete_profile`), because an entry surviving elsewhere would come back as a tab pointing at a connection that no longer exists.
    - **`active_environment_mut()` is the only way to reach the active environment for writing.** It creates one when the list is empty and *re-anchors* a dangling `activeEnvironmentId` rather than just working around it — leave the id dangling and the fallback re-runs on every call, potentially landing on a different environment each time. `prune()` applies `MAX_REMEMBERED_CONNECTIONS` **per environment**: a global cap would let a busy environment evict a quiet one's tabs.
    - **The migrated/initial environment is created with an EMPTY `name`.** Empty means "never named by the user" and the frontend renders `t("environments.defaultName")` via `environmentLabel()`. Don't write a literal there — the backend picking display copy would freeze one language into the user's data permanently. Same reason the backend never interprets `color`/`icon`.
    - **`useEnvironments.switchTo` order is load-bearing** (`src/stores/session/environments.ts`): flush the outgoing session while the backend still points at it → disconnect every pool → **re-save the outgoing `launch` state from the set captured *before* the teardown** → `set_active_environment` → clear the tab store → `restoreSession()`. That third step is not redundant: `useConnections.disconnect` persists the launch state as it goes, so after the loop the outgoing environment believes nothing was open and returning to it would restore an empty session. The last write wins, and it has to be ours.
    - **A per-connection *view* filter is environment state, not profile state — but the profile stays its default.** `visible_databases` ("Bases de datos a mostrar") lived only on the global `ConnectionProfile`, so narrowing a shared test server to one client's database from inside a "Producción" environment also narrowed it in the environment that server belongs to (the same bug `visible_connections` had one level up, before it moved onto `LaunchState`). It is now resolved in two layers by `useVisibleDatabases` (`SchemaExplorer.tsx`): **`LaunchState.databaseVisibility[connectionId]` if the key is present, otherwise `profile.visible_databases`.** The map's value is itself nullable — a stored `null` means "show all *here*", which is the only way an environment can widen a subset the profile narrows, so never collapse `undefined` (no override) and `null` (override to all) into one thing. The profile keeps the field because it is what travels through export/import and shared origins; the picker writes the override by default and only touches the profile when the user picks "all environments" (in which case it also *clears* the override, or the profile-wide choice would be invisible where they made it). Don't "simplify" this by cloning the profile per environment: that duplicates credentials and keychain entries, opens a second pool against one server, and breaks the bullet above. Unlike the id lists, `delete_profile` sweeps this map — a keyed payload is worth reaping.
    - **The three view filters in `restoreSession` are restored *before* the `reconnectOnLaunch` gate**, everything else after it. They describe how the environment looks (folds, `visibleConnections`, `databaseVisibility`), not what it reopens; `persistLaunchState` writes them regardless of the preference and `switchTo` clears them on the way out, so gating their restore left the *previous* environment's filters on screen with reconnect off. Keep new view-only state on that side of the gate and anything that opens a pool on the other.
    - `restoreSession()` is shared with the `App.tsx` launch effect on purpose — entering an environment is one operation, and its ordering (reconnect → layout → focus, gotchas #8 and #10) is too subtle to maintain in two places.

28. **`src/components/` is grouped by domain, each with an optional `dialogs/` subfolder, and one file is one component's worth of work — this reverses the earlier "flat layout is fine" call.** That call was made at ~13 files; by the time it was revisited the directory held 46. The split is two axes: functional domain (`connection/`, `schema/`, `query/`, `grid/`, `menus/`, `shell/`, plus `settings/` and the pre-existing `ui/`), and within a domain, whether the component's main export is a single-purpose modal (`dialogs/`) or not (tabs, trees, panels, bars stay at the domain root). `common/` is reserved for the two components that are genuinely cross-domain leaves (`DriverBadge`: used by ad-hoc/connection-CRUD/tree/status-bar/workspace-picker; `VanishedOriginNotice`: used by the tree, status bar, and the settings Origins section) — don't add to it casually; a component used by 2+ call sites *within the same domain* just lives in that domain, not in `common/`. **A god file is a layout problem too.** Five files had grown past ~1000 lines by carrying things that only *rendered* together: the explorer's eight dialogs and its four tree levels, the connection manager's rail and its form model, the CLI intent block inside `App.tsx`, `TabbedArea`'s tab header and empty state, and `DataGrid`'s row, chips, search box and draft row. They are now one file per level (`SingleDbExplorer` / `MultiDbExplorer` / `SchemaTableSection` / `SchemaTableRow`, `GridRow` / `ServerFilterChips` / `GridSearchInput` / `DraftRowView`, `ConnectionRail`, `WorkspaceTab` / `EmptyWatermark`), with the no-JSX logic in hooks under `lib/` (`useGridSelection`, `useColumnSizing`, `useCtrlWheelZoom`, `useConnectionForm`, `useCliIntents`). Two rules came out of doing it, and both cost a bug the first time they were ignored: **a hook is not a child component** when its effects must keep their position in the parent's effect order (`useCliIntents` — a child mounts *first*, which would put the CLI ahead of the launch-restore sequence of gotchas #8/#10); and **a wide hook signature is a cost to weigh, not an automatic veto**. That second rule started life as "stop extracting when the seam needs the whole component's state", on the grounds that `DataGrid`'s keyboard navigation, its `columns` memo and its toolbar each touch fifteen-plus pieces of grid state. They were extracted anyway in a later pass (3592 → 1301) and the reason the earlier call was wrong is the part worth keeping: what matters is whether a seam **owns** state or merely **borrows** it. `useCellEditing` and `useGridKeyboardNav` own theirs — four `useState`s and `activeCell` leave the component outright — so their inputs are identity props, not a live copy of the grid. The two that only borrow still earned the move, on different grounds: `useGridColumns` because its dependency array is a correctness invariant that should be read next to what it guards, `GridToolbar` because it is a self-contained widget. Where the input list stays long it is **grouped and named** (`grid`, `editing`, `display`, `meta`) rather than flattened, and each hook's doc says outright that the coupling is real. `DataGrid` still takes 41 props; none of this reduced that, and none of it was meant to. `CellEditor.tsx` is the one deliberately borderline case: it's dual-mode (a modal by default export, plus `CellEditorBody` re-exported for `SideEditorPanel`'s docked usage) and was filed under `grid/dialogs/` because the modal is its primary reason to exist. Every internal cross-import in `components/` — and `App.tsx`'s ~22 direct imports — already used the `@/components/...` alias (never relative) before this move, so relocating a file never required touching that file's own imports, only the imports *of* it; that invariant is why the move was a mechanical rename + specifier rewrite with zero logic changes, and it's worth preserving going forward (don't introduce relative cross-file imports at the `components/` top level, even between siblings in the same domain folder — keep using the alias, matching everything outside `settings/sections/`, which is the one pre-existing exception).

29. **The list view edits with the *server's* types, not the display JSON's — `QueryResult.row_types` exists for that and must stay aligned with `rows`.** `bson_to_json` is lossy on purpose (gotcha #17's philosophy): `Int32`/`Int64`/`Double` all reach the frontend as a JSON number and `ObjectId`/`Date`/`Decimal128` all as a string. That was harmless while the list view (`components/grid/DocumentListView.tsx`) was read-only; the moment it started writing, inferring a type from the value would have rewritten a `Long` as an `Int` the first time someone fixed a typo in it — and `301353073` fits in an `Int32`, so the bug is invisible in testing and permanent in the data. `docs_to_result` therefore ships a parallel `row_types` (one `bson_type_tree` per cell: a scalar is its type name, a document/array is an object/array of the same shape), and every write sends that type back as `update_cell`'s `column_type`. Keep the two arrays cell-aligned, and leave `row_types` `None` for the SQL drivers — **their** hint has to stay the catalog type, because `update_cell` reads it to decide whether a MySQL `BIT` needs its `CAST` (gotcha #15); handing it the list view's `"string"` would both miss the cast and suppress the backend's catalog fallback. Two more rules the same fidelity concern imposes: a field is addressed by its **path** (`customData.format`, `tags.2` — dotted, so `$set`/`$unset` take it as-is), never by a display index (gotcha #7, one level down); and types whose display form can't be parsed back (`Binary`, `DbPointer`, `MinKey`, `MaxKey` — see `OPAQUE_TYPES` in `lib/grid/documentTree.ts`) are **not** editable inline, because committing the text `Binary(Generic, 12 bytes)` would store exactly that string. The type picker is their escape hatch, and it is MongoDB-only: `onFieldDelete`'s presence is what switches the component into document mode (add/delete/retype), since a SQL row's column set belongs to the table, not the row.

30. **Every place the generated SQL differs per engine goes through `db::sql::Dialect` — there is no `pg_or_sqlite` bool any more, and no second driver enum.** `Dialect` (`Postgres | Mysql | Sqlite | MsSql`) owns `quote_ident`, `placeholder`, `cast_to_text`, `like_kw`, `not_like_needs_lower`, `like_escape_clause`, `paginate`, `truncate_stmt`, `qualify` and `qualify_defaulted`; `Dialect::try_of(&DbPool)` is the single conversion point and returns `UnsupportedDriver` for MongoDB (not a SQL dialect — it is dispatched to `db::mongo` before any SQL is built). `db::ddl::Driver` used to be a *second*, 3-variant enum with its own `quote()`, and `commands::structure`/`commands::view` each had their own `driver_of()`; all of that is gone. Two `qualify` flavours exist on purpose: the browse path uses `qualify_defaulted` (pins Postgres's `public` / SQL Server's `dbo` so an unqualified name can't resolve through `search_path`), the DDL path uses `qualify`. When adding a dialect, the compiler finds the exhaustive matches — but **audit for `_ =>` arms**, which is how a new engine silently takes Postgres's path (`db::ddl`'s `build_alter` / `drop_index_stmt` / FK-drop were exactly that). `commands::schema`'s `TRUNCATE` was claimed here as fixed while it was still a `_ =>` arm — it now lives on `Dialect::truncate_stmt`, spelled out per dialect and unit-tested without a pool, which is the shape to copy. The same audit applies one level down to matches over *narrowed* sets: `commands::query`'s filter builder had `_ =>` arms inside its comparison and `LIKE` arms, so a new `FilterOp` compiled clean and silently behaved as `<=` / `EndsWith`; those now list every variant, with the impossible ones grouped into an explicit `unreachable!` so adding one is a build error.

31. **SQL Server is a *SQL* driver with a *non-sqlx* client — the hard parts are the pool and four T-SQL divergences.** `sqlx` dropped MSSQL after 0.6, so `db/mssql/` wraps `tiberius`. Unlike MongoDB it does **not** opt out of the SQL path; it rides `Dialect::MsSql` (brackets, `@P1`, `NVARCHAR(MAX)`, `OFFSET/FETCH`). Things that will bite:
    - **`tiberius` has no pool and `Client::query` takes `&mut self`**, so `MsSqlPool` is ours: a `Semaphore` sized from the endpoint budget the pool was granted (`PoolLimits::max_connections`, *not* a constant of the driver's own — `DEFAULT_MAX_SESSIONS = 4` is only the fallback when that doesn't convert) + a stack of idle clients + a `PooledClient` guard that returns its session on `Drop`. The load-bearing rule is in `PooledClient::classify`: a session goes back to the pool **only** when the error was `tiberius::error::Error::Server` (the server rejecting a statement). Anything else (I/O, protocol, TLS) means we don't know where we are in the TDS stream, so the session is dropped — reusing it would corrupt the *next* caller's query, not this one. That's why the command layer never touches a raw `Client`: it gets `query_rows` / `execute` / `simple_query_sets` / `scalar_i64` and the decision lives in one place.
    - **`OFFSET … ROWS FETCH NEXT … ROWS ONLY` requires an `ORDER BY`.** `Dialect::paginate` injects `ORDER BY (SELECT NULL)` when the user hasn't sorted. This is why the driver's floor is **SQL Server 2012**; 2008 would need a `ROW_NUMBER()` window.
    - **Generated keys use `OUTPUT INSERTED.<pk>`**, not `SCOPE_IDENTITY()` — it also recovers a `uniqueidentifier`/sequence default, not just IDENTITY. But SQL Server refuses `OUTPUT` on a table with triggers (**error 334**), so `insert_row` detects that code (`db::mssql::is_output_clause_conflict`) and retries with `SCOPE_IDENTITY()`. Don't "simplify" this to one path.
    - **Binary columns need `CONVERT(varbinary(max), @P1, 1)`** (`db::mssql::binary_convert`). This is gotcha #15's trap again: values travel as text, and T-SQL's implicit nvarchar → varbinary conversion reinterprets the *characters*, so saving the `0x4A2B` the grid shows would store the ASCII of that string. Driven off the frontend's `RowValue.columnType` hint. `bit`, dates, numbers and even `uniqueidentifier` coerce correctly and need nothing.
    - `bit` is decoded as the **number 0/1**, not a JSON bool, so the grid's BIT display preference and `BitInput` keep working (same call as MySQL's `TINYINT(1)`); `decimal`/`numeric`/`money` decode as **strings** to avoid `f64` rounding.
    - `update_cell`'s multi-row guard is a real transaction, but via `BEGIN`/`COMMIT`/`ROLLBACK` *statements* on one held session — `tiberius` has no transaction handle.
    - **Deferred on purpose**: the structure editor's DDL, table/view rename (`sp_rename`), *creating or redefining* a view, and `.sql` export/import. `db::ddl::reject_unsupported` and `db::view_ddl::build_view_ddl` refuse `MsSql` up front, which is what makes the `unreachable!` arms below them genuinely unreachable. Note `build_view_ddl` lives in **`db/view_ddl.rs`**, a sibling of `db/ddl.rs`, not inside it. *Reading* a view's definition is NOT deferred — `db::mssql::schema::view_definition` reads `sys.sql_modules`, since the missing piece was only ever the T-SQL DDL builder; nor is dropping one. The frontend hides those affordances through the capability gates in `src/lib/db/driver.ts` (`supportsDdlEditing` / `supportsSqlDump` / `supportsCreateDatabase`) — add to those rather than writing `driver !== "sqlserver"` inline.
    - **A named instance can't be tunnelled**: the SQL Browser is a separate UDP service, so `db::mssql::open_pool` refuses the combination instead of silently connecting to the wrong port.
    - `AuthMethod::Windows` (NTLM) is `cfg(windows)`-gated *inside tiberius*, so the arm is `#[cfg(windows)]` and the CI's Linux leg compiles SQL-login-only. The connection dialog hides the mode off Windows.
    - Its `rustls` feature pins `tokio-rustls 0.24` → **rustls 0.21 alongside the tree's 0.23**. Accepted knowingly (the alternative, `native-tls`, drags OpenSSL onto the Linux leg); revisit on any `cargo update` that lets tiberius move up.

32. **The command palette's *index* lives in `src/lib/commandPalette/`, never in the component — and "go to this setting" is a string contract between two files.** `CommandPalette.tsx` is presentation + keys only; `useCommands.tsx` builds the entries, `types.ts` owns the group order and the `>`/`@`/`#`/`?`/`:` mode prefixes, `fuzzy.ts` scores them, `settingsRegistry.ts` indexes the individual preferences. Things that will bite:
    - **A palette entry's `id` is the MRU key** (`stores/dialogs/commandPalette.ts` persists the last 12 to `localStorage`), so it must describe *what the entry is* (`table:<conn>:<schema>.<name>`), never its position in the list. A stale id — deleted connection, closed tab — is skipped when the list is rebuilt, which is why no pruning exists.
    - **`SETTINGS_INDEX[].prefId` must equal the `prefId` passed to that setting's `PrefRow`.** That string is the entire join: `useSettingsDialog.openAtPref(section, prefId)` opens the section, and the matching `PrefRow` scrolls itself into view and flashes. A typo degrades silently to "the section opens, nothing is highlighted" — there is no compile-time link. Adding a preference means touching both (and `ShortcutRow` already emits `keybinding.<ActionId>` for every entry in `ACTIONS`, so shortcuts come for free).
    - `PrefRow` consumes `highlightPrefId` immediately (`clearHighlight` on match, not after the timeout) so re-opening the same section later doesn't replay the flash, and `setSection` drops a pending highlight — the user navigated elsewhere.
    - **`useCommands(enabled)` returns `[]` when the palette is closed.** It is mounted for the app's whole life; indexing every table of every connected database on unrelated store changes would be pure waste. Keep new providers inside that gate, and keep reading raw store state (gotcha #1) — the memo derives, the selectors don't.
    - **Alt+Enter is a per-entry second action** (`PaletteCommand.alt`), and a `keepOpen` one is deliberately *not* remembered in the MRU: reordering the empty-query view mid-toggle would slide the row out from under the cursor.
    - **`useUi.selectedConnectionId` must always name a real profile — pass every cross-connection navigation through `parentConnectionId` (`lib/connectionLabel.ts`).** A tab or table of a multi-DB server carries the synthetic `<parent>::db::<db>` id, but `useConnections.active` only holds top-level ids (`markConnected` runs in `connect()`, never for `open_database_view`), and `App.tsx`'s sync effect clears any selection missing from that set — so selecting a child id is undone a render later and replaced by whichever pool came first. This bit the tab switcher silently before the palette ever existed.
    - **The table index is only as warm as the tree.** A server-wide connection's per-database tables live under child slices that exist only once a view is opened, so `@` also offers an explicit "index all databases" entry (`warmSchema.ts`) — bounded to 3 concurrent opens with a connection-limit circuit breaker, because each view is another pool. Never make this an automatic per-keystroke fan-out; that is exactly the bug the explorer's prefetch had to fix.
    - Three dialogs the palette needs were local `useState` in `FileMenu` and now live in `stores/dialogs/connectionDialog.ts`; `FileMenu` is still their only mount point. `TabbedArea`'s own `ConnectionDialog` is a separate, tab-scoped flow and intentionally stays local.

33. **A MongoDB "view" is a stored pipeline, so the view *editor* for it is the *aggregation* editor — and there is exactly ONE parser for a pipeline, in Rust.** `commands/view.rs`'s `preview`/`apply` commands reject Mongo on purpose (nothing to diff: no `CREATE VIEW` body, just `{create|collMod, viewOn, pipeline}`); the parallel path is `db/mongo/aggregation.rs` + `commands/aggregation.rs` + `src/components/aggregation/`. **The two editors still diverge, but the MCP surface does not**: `get_any_view_definition_inner` / `save_any_view_inner` / `drop_view_inner` in `commands/view.rs` dispatch across both models, because an AI client cannot tell them apart from a `list_tables` row and wants one tool per verb, not two. That is the same call `drop_view` had already made for itself. The GUI's divergence is right (a pipeline builder and a SQL text editor are different surfaces); a headless caller's would not be. The invariants:
    - **The frontend never parses a pipeline.** Stage bodies cross the IPC boundary as the *source text* the user typed — relaxed JSON, `ObjectId(…)`, comments — and are read by `shell::parse_relaxed_value`, the query editor's own parser (now callable standalone, and comment-aware; `skip_ws` handles `//` and `/* */`). That is also why the stages ⇄ text mode switch is a backend call (`format_mongo_pipeline`) and not a client-side split: an array literal cannot be split on commas, a stage body is full of them. `lib/mongo/pipeline.ts::operatorOf` reads only as far as the first key — enough to label a card, never enough to be mistaken for a parser. Don't add a JS pipeline parser; the two grammars would drift and the drift would be silent.
    - **Reading a view back goes through `values::bson_to_shell_text`, not `bson_to_json`.** The stored pipeline is BSON; rendering it with the display converter would turn an `ObjectId` in a `$match` into a bare string and a `NumberLong` into a plain integer, so *opening a view and saving it unchanged* would quietly stop it matching anything (gotcha #29's failure mode, one level up — and an `Int64` is written as `NumberLong(…)` even when it fits an `i32` for exactly that reason). The `pipeline_source_round_trips_through_bson` test is the guard. Types with no constructor in the grammar (`Binary`, `Timestamp`, `MinKey`/`MaxKey`) fall back to Extended JSON and are the documented lossy edge.
    - **`$out`/`$merge` are refused before dispatch** (`reject_write_stages`), in previews *and* in saved views. The editor previews on a debounce as you type, so running a write stage would overwrite a real collection mid-edit. Every preview also appends `{$limit: n}`, and the per-stage preview runs the pipeline *prefix* per stage — bounded work per keystroke, not a full materialisation.
    - `docs_to_result` is `pub(super)` so the aggregation module shapes its output identically to `find`/`aggregate` in the query editor, `row_types` included (gotcha #29). Previews mount `DocumentListView` read-only: a pipeline's output is computed, there is no `_id` to write back through, and omitting `onFieldSave`/`onFieldDelete` is what keeps that component out of document-editing mode.
    - Aggregation tabs are ephemeral (filtered out of `persistedTabs`, like structure and view tabs) but ARE deduped in `useTabs.open` on (connection, schema, table, **view**) — so "Edit pipeline" on a view and a scratch pipeline over the same collection stay separate sessions, and re-opening either can't strand a pipeline mid-build.

34. **MongoDB indexes are read from the RAW `listIndexes` documents, never from `mongodb::IndexModel` — and there are now TWO index readers on purpose.** `db/mongo/schema.rs::list_indexes` feeds the SQL-shaped explorer DTO (`commands::schema::IndexInfo`: name + column *names* + `unique`) and is deliberately lossy; `db/mongo/indexes.rs::list_indexes` feeds the index manager and is not. Don't "deduplicate" them — the whole point is that the second one exists because the first can't grow without breaking the SQL drivers it also serves. The invariants:
    - **The typed `IndexModel` throws away everything an editor needs**: the per-key direction (`1`/`-1`) and type (`text`, `2dsphere`, `hashed`), `sparse`, `expireAfterSeconds`, `partialFilterExpression`, `collation`, `weights`, `hidden`. Rebuilding `{ createdAt: -1 }` from a field-name list recreates it *ascending* — invisible in testing, permanent in the data, gotcha #29's exact failure mode. The raw reply document preserves key order, key values and every option, and whatever `MongoIndexInfo` doesn't model explicitly survives in `extra_options` as source text (with `NOISE_OPTIONS` — `v`, `ns`, the `*IndexVersion`s — filtered out because the server owns them). Writes use `createIndexes`/`dropIndexes`/`collMod` run-commands, not `Collection::create_index`, which is lossy in the outbound direction for the same reason.
    - **Same one-grammar rule as #33**: key documents, partial filters, collations and weights cross the IPC boundary as source text and are parsed by `shell::parse_relaxed_value`, rendered by `values::bson_to_shell_text`. `lib/mongo/indexKeys.ts` recognises the six pickable key values and assembles source text — it is not a parser, and an index whose keys it can't express opens in the dialog's **raw** mode from `keysSource` rather than being flattened into something the picker can show. That is why `keysSource` crosses alongside the parsed `keys`.
    - **`_id_` is refused in the backend** (`reject_id_index`), not only greyed out in the UI. **A blank optional document is `None`, never `{}`** — `{}` is a *meaningful* partial filter (matches everything), so collapsing the two would build a different index than the one asked for.
    - **"Edit" is drop + create** — `collMod` reaches `hidden` and nothing else — so `recreate_index` parses and validates the new spec *before* dropping, and its post-drop failure message names the now-missing index. **Hide is the reversible rehearsal for drop** and is why it sits next to it in the row menu.
    - Sizes (`$collStats` → `indexSizes`) and usage (`$indexStats` → `accesses`) are **best-effort**, like `schema.rs::collection_sizes`: a role without the privilege leaves them `None` and the UI drops the column entirely rather than rendering a column of zeros that reads as "unused". Index tabs are ephemeral and deduped on (connection, schema, table). Not exposed over MCP — these are writes, and that's a write-policy decision, not a UI side effect.

35. **An environment's export is its *portable identity* — cosmetics + connections + origins — never its tabs, layout or launch state, and import always creates NEW environments.** `export_environments`/`analyze_environment_import`/`import_environment` (`commands/prefs.rs`) round-trip an `EnvironmentExportFile` (`transfer.rs`), which shares `ExportMetadata` with the plain profile-bundle `ExportFile` via a `meta.kind` discriminant (`"profiles"` vs `"environment"`, defaulting to `""` ≡ `"profiles"` for files written before the field existed) — each importer rejects the other's file with a clear error instead of silently importing half of it.
    - **A single export can bundle more than one environment.** `EnvironmentExportFile.environments: Vec<ExportedEnvironmentBundle>` plus one **deduplicated** `profiles: Vec<ExportedProfile>` pool — not one copy of `profiles` per environment. Two selected environments sharing a connection (a common "Producción"/"Staging" split against the same jump box) would otherwise duplicate that profile, its secrets, and, on import, its keychain entry. Each bundle instead lists which of the shared pool it references via `connection_ids` (original, pre-import ids). `export_environments(ids: Vec<String>, …)` takes the whole selection at once — the frontend's `ExportEnvironmentDialog` is a checklist (mirroring `ExportProfilesDialog`), reachable both from File → "Export environments…" (defaults to everything checked) and from a per-row shortcut in `EnvironmentSwitcher` (pre-checks just that row) via the shared `useEnvironmentTransfer` store's `openExport(ids?)`.
    - **Tabs/dockview geometry/launch state are deliberately excluded.** They're session artifacts tied to the machine that produced them (gotcha #10's dockview blob is keyed to that machine's `useTabs` panel ids), not part of what makes an environment portable. What travels is the environment's cosmetics (name/color/icon/theme) plus the connection profiles it references — resolved by `referenced_profile_ids` as the union of `connections` map keys, `launch.active_connections`, `selected_connection_id`, `visible_connections` and `database_visibility` keys, since none of those individually is guaranteed to list every connection the environment has ever touched.
    - **Import never merges.** Every bundle in the file mints a fresh environment id, which is what makes conflicts a non-issue for everything except connection profiles (`profiles.json` is global, so those genuinely can collide) — resolved **once for the whole file**, not per environment, reusing `import_profiles`'s exact `ConflictAction`/`ImportResult` machinery via the extracted `apply_profile_imports` (`commands::connection`). That function's second return value is an original-id → new-id map, which `import_environment` uses to translate each bundle's `connection_ids` into `launch.visible_connections` for its new environment — a skipped profile simply has no entry and is dropped from that environment's filter. Origins and each environment's own cosmetics never need a resolution step: there is nothing pre-existing for a brand-new environment to conflict with.
    - **An origin's export is name + path only, never a passphrase** — same threat model `origins.rs` already documents (the secret travels out-of-band). An imported encrypted origin surfaces the same "no passphrase stored" state a freshly `add_origin`-ed one would; there is no special "needs passphrase" step in the import result, because the existing per-origin sync-error surfacing (`useOriginSync.errors`) already covers it.
    - **Each new environment's connection tree is scoped via `launch.visible_connections`**, not a new mechanism — set to exactly its bundle's (translated) profile ids so the environment reads as "these connections", the same DataGrip-style filter #107 already added. None are auto-connected (`launch.active_connections` stays empty): importing an environment must not silently open N live database connections.

36. **`refresh` in `useSchema` means the whole schema, and on a multi-DB connection the id you hold is almost never the one to refresh.** Two independent traps, both fixed but easy to reintroduce:
    - **The tables of a server-wide connection live in the synthetic `<parent>::db::<db>` child slices, never in the parent's.** The parent's `list_tables` answers for the login's default database on Postgres and for *nothing* on MySQL (`SELECT DATABASE()` is NULL → `Ok(vec![])` by design — issue #52). So `refresh(parentId)` re-fetches a list nobody renders and leaves the visible subtree untouched — which is exactly why "Refresh" looked broken for a table created outside the app. **Anything holding a profile id (the connection row's menu, the command palette, the `refreshSchema` keybinding — `useUi.selectedConnectionId` can only ever be a profile id, gotcha #32) must call `refreshTree`, which fans out to every child slice opened beneath it.** The Database node refreshes its own child explicitly via `resolveChildId`. `databaseViewId`/`isDatabaseViewOf` live in `lib/connectionLabel.ts` next to `parentConnectionId` — don't spell `::db::` out a second time.
    - **`refresh` must invalidate `columns`/`indexes`/`columnErrors`/`indexErrors`, not just replace `databases`/`tables`.** `TableRow` loads a table's columns only when the key is *absent* (`if (!cols && !colError)`, a deliberate guard so collapsing and re-expanding doesn't re-query), so anything left in those maps is permanent until `drop()` on disconnect: an `ALTER TABLE ADD COLUMN` performed outside the app was invisible forever. The wipe is paired with an immediate re-load of the tables whose node is still in `expanded`, captured *before* the wipe — without that, an open node comes back empty and nothing would ever fill it.
37. **SQL Server accepts SSMS's `HOST\INSTANCE` in *either* field, and `split_instance` (`db/mssql/mod.rs`) is the one place that knows it.** SSMS has a single "Server name" box, so that is the form users type; unsplit it fails two different ways (a backslash in the host breaks DNS; the whole string as an instance name can never match the SQL Browser, which reports only the bare name). The normalisation runs in `open_pool` **before** the tunnel branch — the tunnel is opened against the host — and `build_config` takes the instance as a parameter rather than reading the profile, the same contract `host`/`port` already had. `lib/db/driver.ts::splitSqlServerName` is a UI-only twin so the dialog can show the split on blur; the Rust one is authoritative (it also serves the CLI and the MCP connector). Related: `Reach::Browser` carries the static port as a fallback for a stopped/firewalled SQL Browser (UDP 1434), but only when the user set a port other than 1433 — retrying the default on a host that is dropping UDP just buys a second connect timeout.
38. **MongoDB *can* rename a collection; only a *view* genuinely can't.** `renameCollection` is an `admin`-database run-command taking fully-qualified `db.collection` on both sides, which is also why moving to another database is the same call (`db/mongo/schema.rs::rename_collection`, dispatched from `rename_table`'s Mongo arm). `dropTarget` stays `false` — a rename onto an existing collection must error, not silently drop it — and a view is refused before the round trip with a message telling the user to recreate it. The UI gate is `supportsRenameTable`, **not** `supportsDdlEditing`: rename needs no DDL builder, which is the whole reason MongoDB has it while structure editing stays read-only there. A cross-database move closes the collection's tabs instead of retitling them (`closeTabsForTable`) — the destination is behind a different `<parent>::db::<db>` connection id, so a retitled tab would keep querying the database the collection just left.

39. **A JSON Schema binding is *local metadata* resolved by a cascade that exists only in Rust — and the library is global, not per environment.** The feature is a library of user-authored schemas (`json_schemas.json`, owned by `src-tauri/src/json_schemas/`) plus a list of bindings attaching them to columns, feeding Monaco's already-bundled JSON worker. The things a future session would get wrong:
    - **Global, and in a file of its own.** A binding is `(table, column)`, so it describes the *server*, not the Producción/Staging axis: putting it on `Environment` reproduces the `visible_databases` bug (gotcha #27) a third time, and `tab_state.json` is LRU-pruned, which a user-authored library must never be. Not `prefs.json` either — a body is 50–200 KB and `prefs.json` is rewritten (debounced 400 ms) on every `Ctrl`+wheel of the grid. The precedent is `GridPrefs::column_widths`: also per-table-column, also global.
    - **`body` is source text and the backend never parses it.** `serde_json::Map` is a `BTreeMap` unless `preserve_order` is on, so a `Value` would silently re-alphabetise the user's keys on every save; enabling that feature is worse, since it is *global* to `serde_json` in this tree and would reorder every `Value` in the app (BSON conversions, Extended JSON, `internal_layout`). Keeping the body opaque also keeps gotcha #33's one-parser rule true for free: the only JSON Schema parser in the product is the one inside Monaco's worker.
    - **The cascade is Rust-only. Do not mirror it in TypeScript.** `resolve_json_schemas_for_columns` answers for a whole relation in one call (once per data tab, never per cell) and the single-column variant covers MongoDB dotted paths, which are not known until the user expands a field (gotcha #29). Granularity, not language, is the answer to the performance objection. A resolution bug is not an error — it is "the completion did not appear" — so drift here would be permanently invisible (gotchas #30/#33). Specificity is `column > table > db_schema > connection`, and connection being the **lightest** axis is load-bearing: a whole-connection blanket rule must lose to one naming the exact table and column, while connection breaks ties between otherwise identical rules. `column`'s glob treats `.` as a literal, so a binding on `customData` does not leak onto `customData.format`. Every resolution command folds a synthetic `<parent>::db::<db>` id through `parent_connection_id` first — forget that and bindings silently never match on a server-wide connection (gotchas #32/#36).
    - **Validation must never gate a save.** Nothing in the commit path reads markers and `schemaValidation` is pinned to `"warning"`, so a violation does not even look like it blocks. The database is the authority.
    - **Three Monaco traps, all verified against the worker source and all surfaced in the UI rather than hidden** (`src/lib/monaco/monacoJson.ts`): `setDiagnosticsOptions` is a *total replacement* that stops the JSON worker and recomputes every JSON model's markers, so the schema array is rebuilt from a map behind a signature guard and never per keystroke; an unresolvable `$ref` does not merely warn — it cancels validation of the whole document, which is why `collectExternalRefs` exists and why `enableSchemaRequest: false` is passed explicitly; and a document's own `$schema` key **takes precedence over `fileMatch`**, so a configuration blob that declares one ignores its binding entirely (the badge says so). Two things need no work: the draft-07 meta-schema already ships inside the worker, and the diagnostics adapter already debounces at 500 ms.
    - **A cell editor's model `path` must be stable *and* carry its surface.** Schemas attach by `fileMatch` against the model URI, so the default `inmemory://model/N` can never match; and `@monaco-editor/react` looks a model up by path and disposes it on unmount, so the modal and the docked panel sharing a path would have the first to unmount destroy the other's model. The nonce is `editorKey`, which makes "changed path" and "remounted" one event.
    - **In the structure editor a binding lives OUTSIDE `WorkingColumn`.** `desired` is built with `columns.map(({ _key, ...c }) => c)`, so a field on the working column rides into the `preview_structure_change` payload and re-triggers the debounced DDL preview on every pick. A separate map makes that impossible by construction, not by discipline (gotcha #16). That surface is also an *addition*: `supportsDdlEditing` excludes MongoDB and SQL Server, and MongoDB benefits most — the badge is the universal path.
    - **The change event is a global `emit` and the bridge listens WITHOUT a `target`.** That looks like gotcha #25's cross-window leak and is its deliberate opposite: that bug was a per-window payload reaching every window, whereas this is one global file whose cached resolutions go stale everywhere at once. Scoping it would mean a schema edited in one window silently not applying in another. Its payload is `()` and the listener re-fetches — shipping the library would reintroduce the cost of living in `prefs.json`.
    - **Writes are per item** (`save_profile`'s shape, not `update_preferences`'s): a whole-blob save would let two windows editing different schemas clobber each other, which is issue #18 exactly.
    - **Deleting a profile sweeps its bindings; deleting a schema cascades to them.** A profile id is a uuid that is never reused, so such a binding is provably dead rather than inert-but-meaningful — a keyed payload worth reaping (gotcha #27) — and the asymmetry is what makes it safe: the schema, the expensive artefact, is never touched. Related: `apply_profile_imports` mints a fresh uuid even on `Overwrite`, so it returns the overwrite subset of its id map and both callers repoint bindings through `remap_connection_ids`. Nothing depended on that id before, which is why the bug was invisible.
    - **On import, a binding whose connection is unknown locally is DISABLED, keeping its original id.** Widening it to a wildcard changes what the rule means; dropping it loses intent with no way to notice. Schema conflicts key on **name**, not id (unlike `transfer::detect_conflicts`): two machines mint independent uuids for "the same" schema, so the id can never collide and the name always will.
    - **Don't call it the MongoDB collection validator.** `docs/MONGODB_ROADMAP.md` item #2 is a *different* feature — a server-side `$jsonSchema` enforced on writes, in a BSON-flavoured dialect. Keep the nouns apart in UI copy and docs, or support answers the wrong question forever.

40. **Shared origins (#108) are a GLOBAL registry (`tab_state.json` v5, `PersistedTabState.origins`) — they used to live on `Environment` and that was wrong for the same reason gotcha #39 gives for JSON Schemas.** An origin describes a server-side resource (a file on a share), not a Producción/Staging axis, and what it produces — `profiles.json` entries, whole mirrored environments — is already global. Scoping the *registration* to one environment reproduced the `visible_databases` bug (gotcha #27) one level up: the same physical file needed a second, independent registration (a second id) to be seen from a second environment, and deleting whichever environment happened to hold the registration silently orphaned every connection it had ever imported, with no notice raised at all — worse than an intentional `remove_origin`, which at least tells the frontend. `commands::origins`'s `add/update/remove/sync/list_origins` all read/write `state.tab_state.write().origins` directly now — there is no more `active_environment_mut().origins`. `Environment.origins` still exists as a **deprecated**, always-empty-on-save field (same convention as `ConnectionTabState.internal_layout`, gotcha #10), kept only so an old v4 blob still deserialises.
    - **Migration (v4→v5) dedupes by `path`, not by id.** Two environments that had each registered "the same" shared file independently (two ids, one path) collapse into one global entry on first load after upgrading — first occurrence wins the surviving id, deterministic because environments and their per-env origins keep their on-disk order. Every dangling reference to a deduped-away id — a `ConnectionProfile.origin_id` (in the **separate** `profiles.json`), a mirrored environment's `Environment.origin_id` — is remapped to the surviving id. `tab_state::RawState::into_state_with_remap` returns the remap table (`load_tab_state` now returns `(PersistedTabState, HashMap<old_id, new_id>)`); `state::AppState::new_with_args` is the one place that applies it to `profiles.json`, since `tab_state.rs` has no business touching a different file. Get the load order wrong (profiles before tab_state) and the remap has nothing to apply itself to.
    - **`export_environments`/`import_environment` had to change too.** An environment no longer "owns" origins to copy verbatim into its export bundle; `export_environments` derives `ExportedEnvironmentBundle.origins` from whichever global origins the environment's *referenced connections* (by `origin_id`) or its own mirror (`env.origin_id`) actually depend on. `import_environment` still mints fresh origins per bundle (no dedup-on-import — a rarer case than the migration's, and easy to spot and clean up by hand), but pushes them onto `guard.origins` (global) instead of a per-environment field that no longer exists.
    - **Landing a synced profile's secrets goes through `transfer::land_secrets`, never a local copy.** `sync_origin` had its own decrypt-and-store branch, and it stored the base64 AES-256-GCM *envelope* as the password whenever no passphrase was configured — `build_exported_profiles` always encrypts, so that arm was never correct, and the result was a profile that could not connect and a keychain entry the real password could not be recovered from. The shared function takes a `LandMode`: `Strict` (the profile importer — a secret that will not decrypt fails the import) or `BestEffort` (a sync — skip it and leave the profile asking for a password, which is what an origin without its out-of-band passphrase is supposed to look like). It never writes a secret it could not decrypt, in either mode, and three keychain-free tests pin that down.
    - **`useOriginSync`'s in-memory `vanished`/`vanishedEnvironments` notices are the only thing standing between "removed this origin" and "connection stuck forever read-only."** `noticeOriginRemoved` (called synchronously from `OriginsSection`'s remove flow, before the origin is actually gone) is the well-named, immediate path — but it's in-memory only, so an app restart before the user decides loses it for good, and a profile/environment left with a dangling `origin_id` is read-only in the UI (`ConnectionDialog.isFromOrigin` and the equivalent environment gating) with **no other way to clear the tag**. `reconcileOrphans`, run at the end of every `syncAll()` pass (launch, the 4-hourly poll, "Sync now"), is the durable fallback: it compares every origin-owned profile/environment against the ids `listOrigins()` (now global, so one call covers everything) just returned, and raises the same notice — minus the name, which is unrecoverable by then; the notice components fall back to a translated "a shared origin that no longer exists" when `originName` is blank. Don't remove either path: the proactive one is the good UX, the sweep is the safety net for when it's missed.

41. **Every JSON state file goes through `src-tauri/src/state_file.rs` — path, load and atomic save.** Five modules own a file (`store`→`profiles.json`, `prefs`→`prefs.json`, `tab_state`→`tab_state.json`, `json_schemas`→`json_schemas.json`, `ssh_known_hosts`→`known_hosts.json`) and each used to carry its own copy of the same three steps. Two things came out of that:
    - **One copy had drifted.** `store::save_profiles` wrote with a plain `fs::write` while the other four did temp-file + rename — on the one file whose loss costs the most (every saved connection, plus the keychain entries, JSON-Schema bindings and origin links keyed on those profile ids). `save_atomic` is now the only writer.
    - **Loading comes in two flavours, and the choice is a policy decision, not a style one.** `load_or_default` is silent degradation, correct for preferences and known-hosts: a corrupt file costs a setting, never a launch. `read_bytes` stops one step earlier for the two files whose parse isn't a plain `from_slice` — `tab_state` deserialises `RawState` and returns `(state, origin remap)` after migrating v1–v4, and `json_schemas` has to *warn* about a future-version file rather than replace it. **`store::load_profiles` deliberately uses neither**: it propagates the parse error, because an empty profile list is not a safe default there (see the state-map table).
    - Adding a state file means one `state_file::save_atomic` call, not a new path helper — which is also what keeps gotcha #26's canary rule enforceable in one place instead of six.

42. **`db::sql::Dialect` builds the SQL; `db::exec` runs it. A `match pool { … }` in `commands/` is a smell.** `Dialect` (gotcha #30) owned the per-engine *text* while every command that needed to execute anything wrote its own dispatch over `DbPool`, which is how `query.rs:2368` and `bulk.rs:236` ended up byte-identical, how one Postgres arm re-inlined a decoder that already existed 200 lines above it, and how the same "one DDL statement, no parameters" match appeared seven times. `db/exec.rs` exposes `execute`, `execute_params`, `scalar_i64`, `query_rows`, `execute_all` and `in_tx_expect_at_most_one`; `MsSqlPool` already had that surface, so its arm is one line, and MongoDB is refused with `UnsupportedDriver` (it is dispatched to `db::mongo` long before any SQL is built). Two notes for anyone extending it: the bind loops are **macros** (`bind_all!`, `bind_all_scalar!`) because a generic function cannot satisfy sqlx's per-driver `ColumnIndex`/`Encode` bounds across three drivers; and `query_rows` returns the untyped `(Vec<(String, String)>, Vec<Vec<Value>>)` shape that `db::values`'s `columns_fn!`/`result_fn!` macros generate, so a caller shapes it into whatever DTO it serialises.

43. **Catalog SQL lives with its driver, in `db/<driver>/schema.rs` — the DTOs stay with the command that serialises them.** `commands/schema.rs` used to hold 40–60 lines of inline SQL per driver inside each of its seven `*_inner` functions, plus 17 `unreachable!()` arms, while `db/mssql/schema.rs` and `db/mongo/schema.rs` already did it the other way round. It is now ~250 lines of dispatch and none of those arms. The DTOs (`TableInfo`, `ColumnInfo`, …) deliberately did **not** move: they are the IPC contract, so they belong next to the commands that serialise them, and each driver module mirrors their shape exactly. `db::sqlite::schema::list_databases` is sync and returns a single `"main"`; SQLite's `list_columns`/`list_indexes` take a documented `_schema` they ignore. The same move later took the view-definition reads out of `commands/view.rs`'s own `match` into `db::<driver>::schema::view_definition` — with one exception that is not a violation: `strip_view_header` went to **`db/view_ddl.rs`**, not into the SQLite module, because SQLite and SQL Server both store the whole `CREATE VIEW … AS …` statement and the module that knows how such a header is *built* is the honest owner of taking one apart.

44. **A dialog's submit half is `useAsyncSubmit`, and it keeps `submitting` true after a success.** Ten modals hand-rolled `setSubmitting(true); setError(null); try { … } catch { setError(String(e)); setSubmitting(false) }`, and the missing `setSubmitting(false)` on the success path is deliberate, not an oversight: every success closes or replaces the dialog, so clearing the flag first re-enables the buttons for the frames before the unmount lands — a double-submit window on a `DROP TABLE`. The hook takes no task at construction so a dialog with two actions (commit vs. clear an override) shares one flag and one error slot; validation (`if (!name.trim()) return;`) stays at the call site. Its natural partner is `ConfirmDialog`'s `error`/`children`/`confirmingLabel` slots — a failed destructive action has to say why *in* the dialog, which stays open, so a toast is the wrong surface there.

45. **Three frontend seams whose whole point is a difference the shared code must preserve.** Each of these was extracted *with* its divergence, not despite it — collapsing any of them is a regression, so they are parameters:
    - **`useListNavigation(count, { wrap })`** — the command palette wraps (a long result list is a ring you spin through), the tab switcher clamps (its list is short enough to see whole, and wrapping past the end reads as a jump).
    - **`useUi`'s `LaunchView` helpers** (`currentLaunchView` / `applyLaunchView` / `clearLaunchView` / `emptyLaunchView`) — the three view filters are always read, written and cleared together, but `undefined` (no override) and `null` (override to "show all") must stay distinct inside `databaseVisibility`, which is what gotcha #27 calls the whole point of the two layers. `emptyLaunchView` is the single source of the neutral values so the "clear" and the "fall back" paths cannot drift.
    - **`lib/schema/warmDatabases.ts` vs the explorer's prefetch** — this entry recorded a *deliberate* duplication, and 1.19.0 removed the thing it was defending. They shared `DB_VIEW_WARM_CONCURRENCY` and nothing else, on the grounds that one was a one-shot awaited walk over a fixed list while the other was a re-entrant effect re-deriving its queue every pass, so the tree filled in progressively and a keystroke changed what still got warmed. That second behaviour only ever earned its keep while *typing* was what triggered a warm — which is exactly what gotcha #55 forbids now. There is one scheduler; `lib/schema/warmForSearch.ts` is the tree's entry point into it and deliberately adds no scheduling of its own (it walks connections sequentially, since five at once would be fifteen simultaneous pool opens — the burst the per-connection bound exists to prevent). Kept here as the worked example of a shared-with-a-difference seam whose difference expired: the note is more useful as a record of that than deleted.
    Same family: `useDebouncedPreview`'s 400 ms is shared by the structure and view editors, while `AggregationTab` keeps its own 500 ms — each of its previews runs the pipeline *prefix* per stage, so the work per fire is not comparable. And the two four-hourly polls in `lib/schedule.ts`'s callers stay two constants for the same reason.

46. **The three import dialogs share `lib/transfer/useImportWizard.ts`, and the `"skip"` default lives there.** Profiles, environments and JSON Schemas all run `pick → (passphrase) → (conflicts) → done` over the same nine pieces of state, and their `doImport` bodies were byte-identical including the `listen(IMPORT_PROGRESS_EVENT)` subscription and its `finally` (now `lib/bridges/import-progress-bridge.ts`, so the event has a module like the other seven `huginndb://` events). The default conflict action being in one place is the point: it used to be `"rename"` in one dialog and `"skip"` in the others, which is how re-importing your own export accumulated `name (imported)`, `name (2)`, … on every round trip. Each dialog supplies `analyze`/`run` and an optional `reviewStep`; the conflicts UI is `ConflictResolutionStep`.

47. **`PrefId` is derived from `Preferences`, so gotcha #32's string contract is now a compile error.** `SETTINGS_INDEX[].prefId` and the `prefId` prop on that setting's `PrefRow` are joined by that string alone, and a mismatch used to degrade silently to "the section opens, nothing is highlighted". `lib/prefId.ts` builds the union as `` `${group}.${keyof Preferences[group]}` `` for the four row-rendering groups, plus `` `keybinding.${ActionId}` `` for the shortcut rows (`version` and `keybindings` are not rows, which is why they are excluded from the path side). Adding a preference still means touching both files — the compiler just tells you when you forgot.

48. **A MongoDB view and a collection share ONE namespace, so `drop_view` needs a type check the SQL drivers get from their engine for free.** `db::mongo::aggregation::drop_view` is `db.collection(name).drop()` — literally the same call as dropping a collection. It carried no check for a long time, on the stated grounds that it was "kept separate so the caller's intent is explicit", which is true of the *caller* and says nothing about the *argument*. Intent was actually being supplied by the only caller: `SchemaTableRow` renders "Drop view" only under `isMongo && isView`, so the user had clicked a row the tree already knew about. The moment a caller can pass a name it merely guessed — which is exactly what the MCP connector's `drop_view` tool is — a mistyped plural deletes every document in a real collection and reports success. `view_presence` now resolves a name to `Absent | Collection | View(def)` in one `listCollections` round trip and `drop_view` refuses all but the third; the predicate behind it (`spec_is_view`) is pure so the thing standing between that function and a collection's data is testable without a server, and it treats a spec with **no `type` field as a collection** (the field only appeared in MongoDB 3.4, and an unrecognised reply must fall to the safe answer, not the destructive one). Two consequences to keep: all three states are load-bearing — `save_view` needs `Absent` vs `View` to choose `createView` vs `collMod`, and `describe_table` treats both non-view answers as "no view body" rather than an error — and an absent name is now `NotFound` rather than MongoDB's silent idempotent success, which is what makes the driver *consistent* with the other four (every SQL driver builds a bare `DROP VIEW` with no `IF EXISTS`) instead of the odd one out. The SQL drivers need no equivalent guard: `DROP VIEW` against a table errors on all four.

49. **`bridged_connection_id` (`mcp/mod.rs`) has a `_ => None` arm, so it is the one step of the add-a-write-tool checklist the compiler cannot enforce.** Every other step is protected by an exhaustive `match` — `BridgeRequest::label`, `is_mutating`, `bridge::server`'s `connection_id_of`, and `bridge::exec`'s dispatch all fail to build if a variant is missed. **Correction worth knowing before you trust that list: `bridge::server`'s `policy_id_of` and `class_of` both end in `_ => None` too, so there are *three* unenforced steps, not one — and those two are worse than this one. A write variant missing from `policy_id_of` skips the app-side policy re-check entirely; missing from `class_of` does the same, since `check_policy` returns `Ok(())` the moment either is `None`. The symptom is not a bad log line, it is a write a `read-only` connection was allowed to make.** This one silently returns `None`, and the only symptom is `conn=-` on that write's line in `mcp-audit.log`: an audit-quality regression in a file nobody reads until they need it, long after the change that caused it. When adding a write variant, add it here too. (Do **not** add a read or a dry-run variant — `PreviewViewChange` is deliberately absent, since an unaudited call never reaches this function.) Related, and the reason the audit story needs care at all: writes are audited on *two* paths — bridged, by `AuditSink` in `Huginn::call`, and local, by the `_inner` writing through the `&dyn LogSink` it was handed — so a new write core that does not take a sink is invisible in `mcp-audit.log` whenever no desktop app is serving the bridge, which is the documented fallback rather than an edge case.

50. **The docs viewer derives its navigation from the markdown, and three things about that are load-bearing.** `docs/*.md` are still one file each, still the only source, still read on GitHub unchanged — `src/lib/appInfo/docOutline.ts` slices them at render time into a cover (everything before the first `##`), one page per `##`, and each `###` as a scroll target inside its page. So adding a section to a guide adds it to the sidebar with no code change, and the sidebar translates itself because the Spanish body carries Spanish headings.
    - **One scan produces both the outline and the bodies.** `parseDoc` returns them together rather than there being a heading-lister and a separate splitter, because two passes over the same markdown are two chances to disagree about where a section ends — and that disagreement is not an error, it is a page that quietly loses its last paragraph. There is a round-trip test over the real corpus for exactly this.
    - **The scan must skip fenced code.** `docs/MCP.md` has shell comments at lines 49 and 164 (`# binary at: …`, `# optional: startup_timeout_sec = 20`); a bare `^#` scan reads them as headings, invents phantom sections, *and* truncates the section they sit in. `docOutline`'s fence regexes are copied from `Markdown.tsx`'s deliberately, so the two cannot disagree about where a fence is.
    - **`slugify` is the join between the ids `Markdown` emits and the `#anchor`s already written in the docs**, so it follows GitHub's rule: punctuation is *dropped*, not replaced (`Sharing the app's pools` → `sharing-the-apps-pools`, never `…app-s-pools`). Duplicate-slug suffixing is scoped per rendered body in `Markdown` and per section in `parseDoc`, which is the same scope — render one section and the two agree. A test asserts every anchor in every shipped guide, in both languages, resolves.

51. **`Markdown`'s navigator arrives by React context, not as a prop — and its scroll-to-anchor consumes the anchor *after* the scroll, not before.** Two separate traps in the same component:
    - `renderBlocks` is memoized on `source` alone (`Markdown.tsx`), so a callback threaded down through `renderBlocks` → `renderInline` → `DocLink` would either be captured stale or have to join the dependency array and throw the whole parse away on every parent render. A context that `DocLink` reads during its own render has neither problem. `DocNavigator` is deliberately two methods (`canFollow` / `follow`) so the cursor can tell the truth about a link the host cannot resolve.
    - `DocsDialog`'s `ScrollToAnchor` clears the pending anchor **inside** the `requestAnimationFrame`, after scrolling. Clearing first is the ordering that reads more naturally and does not work: it updates the store, which changes the effect's dependencies, which runs its cleanup, which cancels the frame that was going to do the scrolling — the effect tidies up after itself and never scrolls. `PrefRow` (gotcha #32's settings highlight) clears before its own rAF and may well have the same latent bug; it was not touched here because its flash works and the scroll half was never verified.

52. **`cargo test` writes to the REAL state directory. A test must never reach a function that ends in `save_profiles` / `state_file::save_atomic`.** `state_file::path` resolves through `dirs::config_dir()` + `APP_DIR` with no test override, so under `cargo test` that is the developer's own `%APPDATA%/HuginnDB/`. Three tests written against `commands::origins::merge_profiles_bundle` — whose last statement inside the lock is `store::save_profiles` — therefore overwrote a real 31-connection `profiles.json` with a one-profile fixture, and the *first* symptom was not that: it was two of them failing only in a full run and passing in isolation, because they were racing each other for the same file. Recovery was luck, not design: the app happened to still be running, and since `save_profiles` writes the whole in-memory vector, the next save from the GUI restored everything. The keychain was untouched (the tests never got that far), so the passwords survived; had the app been closed, the metadata was gone. Two rules come out of it:
    - **The fix is a seam, not a mock.** `merge_into` now holds the merge rules and takes `&mut Vec<ConnectionProfile>` plus the live-pool ids, with `save_profiles` left to its caller — the same shape `plan_bulk_delete` / `sweep_tab_state_for_profiles` (gotcha #49's neighbourhood) and `already_landed` / `spec_is_view` already have. Notice what the old shape cost: rules this fiddly (which fields a refresh may overwrite, whether one origin may claim another's profile, what a live pool defers) had **no** coverage at all, precisely because the only entry point insisted on writing to disk first. An untestable function is not a neutral fact about the code; it is an absence of tests.
    - **Before writing a test, follow the call to its last statement.** `AppState::new()` also *reads* the real `tab_state.json` and `profiles.json`, and one branch of `new_with_args` writes them (the origin-id remap). It is read-only in practice, which is not the same as safe by construction — treat a test that constructs it as touching live state.

53. **A keystroke is resolved in exactly one place (`lib/keybindings/dispatch.ts`), and the *scope* that decides whether it applies comes from the DOM.** The subsystem was one 127-line file plus four listeners that disagreed with each other; it is now a catalogue, a pure key lexicon, a resolver and a single stateful dispatcher. The things that will bite:
    - **`resolveBindings` returns a fresh `Map` per call, so it can NEVER be called from a Zustand selector** (gotcha #1). `useKeybindingDispatcher` derives it with `useMemo` from the raw overrides map and reads it through a ref, which is also what lets its `window` listener register once and never re-register on a rebind. The six `getBinding` selectors it replaced were only ever safe because `getBinding` returns a `string`, compared by value — that is still true, and `useShortcutLabel` is built on it for the same reason. If you add a helper here, returning a string is the difference between "safe as a selector" and "infinite render".
    - **A scope is declared with `data-kb-scope` on a container, and `scopesAt(document.activeElement)` walks up to the nearest one.** There is deliberately *no* special case for `overlay`: with a palette open the focus is inside it, so `grid`/`tree`/`editor` are already unreachable, while `global` stays reachable because the palette's own toggle is a global action and has to be able to close it. Two scopes overlap iff they are equal or one is `global` — which is what makes it legal for the grid and the editor to hold the same key, and what `findConflicts` uses so a rebind is only refused when the ambiguity is real.
    - **A binding is a `string[]`, and its three states are all load-bearing**: key absent = use `ActionSpec.defaults`, `[]` = deliberately unbound, non-empty = primary first then aliases. Never "normalise" a reset by writing the default into the map — the Settings screen's "modified" filter and its reset buttons are key-presence checks, and `resetKeybindings` empties the map for exactly this reason. Rust reads both this and the pre-1.19 bare string via `prefs::string_or_vec`; **writes are always the list form**, so a downgrade cannot parse the file and falls back to `Preferences::default()`, losing every preference and not just the shortcuts. That trade is documented at the deserializer; the alternative (a `keybindings2` field with the old one deprecated, the `Environment.origins` shape of gotcha #40) is still available if it ever looks better.
    - **`ActionSpec.fixed` is how a non-rebindable binding is declared** — today only `Mod+R`, which stops the WebView reloading the app out from under an open transaction. It used to be an `if` branch inside `App.tsx`'s handler, which meant the Settings list could not show it and the conflict check could not see it, so rebinding something onto `Mod+R` was accepted and then never fired. Anything reserved goes here, not into a branch.
    - **Monaco keeps its own `onKeyDown`** (gotcha #9 — `addCommand` resolves a bitmask once, inside Monaco's keybinding service, and cannot re-check a live binding) but feeds the *same* dispatcher, so a chord sequence behaves identically inside and outside the editor. It memoizes the resolved index against the overrides object's identity, since the store hands back the same reference until something changes.
    - **The focus guard is `isTypeableChord`, and it is deliberately narrow.** Only a chord with no `Mod`/`Ctrl`/`Meta`/`Alt` *and* a printable token is suppressed inside a text field, so binding an action to a bare letter cannot make that letter untypeable — while `F5`, `Escape` and the arrows keep working with the cursor in an input, which is what anyone expects of a refresh key. The old listener had no such check at all.
    - **`ActionId` is the id namespace for the palette and the menus too.** `PrefId` derives `keybinding.${ActionId}` (gotchas #32/#47), so adding an action grows the palette's settings index and `PrefRow`'s anchors for free — but a new action still needs its `labelKey` in **both** locales, and `actions.test.ts` is what turns that into a test failure instead of a raw dotted key on screen. That test also asserts the shipped defaults do not collide *through the real scope rule*, and that each is stored in canonical form; a default in non-canonical form compiles fine and silently never matches.
    - **Only *overrides* are exported** (`lib/keybindings/transfer.ts`). Writing out each action's effective binding would bake this version's defaults into the file and opt the importing machine out of every default added since.
    - Still open, and they travel together: `CellEditor`'s `Mod+S` is a fixed `addCommand` with a literal hint, and `SideEditorPanel` still wins its `Mod+S` race with `stopImmediatePropagation`. Making either a real catalogue action means making that `addCommand` dynamic, which is the same piece of work.

54. **A statement's write tier is decided in exactly one place (`db/classify.rs`), and the grammar is chosen from the statement TEXT, never from the pool.** Two enforcement points ask the question — the connector's `run_query` (`mcp/mod.rs`) and the app's independent re-check (`bridge::server::class_of`) — and both used to answer it with `db::sql::classify`, a first-keyword heuristic that knows nothing of mongosh. What that cost, and why the fix is shaped this way:
    - **The pool is not available to the question.** `run_query` derived `is_mongo` from `self.state.connections`, and that map is **empty whenever the desktop app is serving the shared pool** (`resolve_mongo_target`'s own comment says so — it pays a `BridgeRequest::IsMongo` round trip for exactly this reason). So every bridged Mongo statement fell through to the SQL classifier, where `db.users.find({})` matches none of `select`/`with`/`show`/`explain`/`pragma` and therefore lands on `DataWrite`: **a `read-only` MongoDB connection was refused its own reads.** `class_of` agreed, for the same wrong reason. Classification now needs no pool at all, which also removes a round trip.
    - **It was a privilege escalation waiting for the grammar to grow.** While `db/mongo/shell.rs` had no DDL, "every Mongo write is `DataWrite`" was merely too strict. The moment `createIndex` / `drop()` / `renameCollection` were added (1.19.0), both sides would have tiered them `DataWrite` and handed a `data` connection the schema changes its policy denies — the exact failure `docs/MCP_CONNECTOR_ROADMAP.md` calls the bar any new write path must clear. `MongoOp::class()` is an **exhaustive** match returning `StmtClass`, so adding an operation without stating its tier is a build error; `is_read()` is now derived from it (`class() == Read`) rather than being a second, independently-maintained list.
    - **An unparseable `db.…` statement is reported as `Ddl`** — the strictest tier. It will fail at parse time anyway when it runs, so the only thing the choice affects is which policies get to *reach* that error, and the safe direction for an authorisation decision is to assume the most.
    - **The whole-relation guard lives here too, and covers both grammars.** `deleteMany({})` used to be accepted at `data` while `DELETE FROM users` was refused at every tier. The opt-in is a trivially-true predicate (`{_id: {$exists: true}}`), mirroring `WHERE 1=1`. `drop()` is deliberately *not* covered: its scope is unambiguous and it already sits behind `full`, exactly as the SQL guard leaves `DROP TABLE` alone.
    - **Don't put the Mongo branch in `db/sql.rs`.** `StmtClass` lives there and that is fine, but a module named `sql` dispatching on a mongosh prefix is what gotcha #30 warns about; the split mirrors `db/exec.rs` vs `db/sql.rs` ("run" vs "build").
    - Related, on the tools added alongside: `create_index` / `drop_index` are **MongoDB-only**, and the reason is the same DTO argument that deferred a structure-editor tool. `db::ddl::IndexDef` is `{name, columns, unique}` because it exists to be *diffed* by the structure editor — `create_index_stmt` / `drop_index_stmt` are private to `build_ddl`, SQL Server has no path at all, and `diff_indexes` is name-based so a same-name column change emits nothing. A SQL client is strictly better served by `CREATE INDEX` through `run_query` at `full`. `NewMongoIndexSpec` is on the other side of that line (a key document as source text plus flags), but the MCP **args struct is flat**, not a nested `spec` object: `schemars` renders a nested struct as a `$ref` into `$defs`, which is what made clients drop every tool in #83.

55. **Typing in the schema tree's filter must never open a connection — and the search has exactly one owner, one debounce and one subscription.** The panel had one filter box that silently applied only to `useUi.selectedConnectionId`'s subtree (`ConnectionsTree` passed `""` to every other connection), so with two connections open one filtered and the other did not, with nothing on screen to explain it — the only marker of "selected" is a 2px hairline, and the selection moves on its own when a tab opens or the palette navigates. Below that sat a second, equally invisible scope: `MultiDbExplorer`'s local `activeDatabaseName`, set as a side effect of expanding a database, which also collapsed its siblings. The redesign inverts the data flow — the tree owns the search and hands *results* down instead of a raw string — and the pieces below are each load-bearing:
    - **Typing opens no pools.** `MultiDbExplorer` used to run a bounded prefetch off its debounced needle: every keystroke walked the databases it had not loaded and opened a `<parent>::db::<db>` view — a whole connection pool — for each. The bound (three at a time, 1.13.0) made it survivable, not right: the unbounded version was itself enough to exhaust a shared server's limit on a nineteen-database box, against a server the user shares with their application, their IDE and any MCP sidecars. A search now reads only what is already in `useSchema`; reaching further is a button on the filter box (`lib/schema/warmForSearch.ts`), which says how many databases it will load and why. **This is the invariant a future performance pass would cheerfully undo**, so it is stated at the top of that file too. It also fixed two silent bugs for free: the prefetch used the bare `api.openDatabaseView` while `warmDatabases` uses `openTrackedDatabaseView`, so a database warmed by searching never got its persistence subscription (gotcha #27); and it applied the visible-databases subset in the warm loop but not in the "are we still prefetching?" check, which is the next bullet.
    - **`0`, "still loading", "never read" and "not searched" are four different answers, and only one of them is `0`.** The old code had one boolean (`prefetching`) computed over `cs.databases` *without* `visibleSet` while the loop that warmed them applied it — so with a subset active it was stuck true forever, `schema.noMatches` could never render, and the user got an empty tree with no explanation. `lib/schema/treeMatches.ts` now returns `pending` / `unloaded` (cold) / `none` / `matches` / `out-of-scope`, in that precedence, and a provisional `0` is what makes someone abandon a search that would have worked.
    - **The scope chip lives on the status line under the box, not inside it.** In the box, in front of the caret, it was the more obvious design and it did not survive contact with the width this panel is actually docked at: a chip reading `Dev | Tencer | MySQL · iMesPyme` left about eight characters of input visible. The flex maths made it worse than it had to be — the input carries `flex-1 min-w-0`, so it is the first thing to shrink and the chip won the space outright — but shoring that up with minimum widths just trades a squashed input for an unreadable chip in a box that has room for neither. Out on the status line it shares a wrapping row with the match summary, so on a narrow panel it takes the line it needs instead of taking it from the input, and it can name a connection *and* a database. Consequence worth keeping straight: the two ✕ affordances now clear what they sit next to (box → the needle, chip → the scope), where a single in-box ✕ used to drop both. `clear()` still drops both and is what entering an environment calls.
    - **`useTreeSearch` is its own store, deliberately not three fields on `useUi`.** `useUi` owns the three *persisted* view filters and their `LaunchView` contract (gotcha #45); an ephemeral search sitting among them is an invitation to add it to `LaunchView` → `LaunchState` → the Rust struct, where it either vanishes at the IPC boundary (gotcha #14) or — worse — does not: a restored needle would paint every connection folded with a `0` badge for the length of the launch reconnect. Nothing here is persisted, and the scope is safe to keep in memory only because `clear()` drops it together with the needle, so a scope can never outlive the search that motivated it. `pendingChord.ts` is the precedent for the shape.
    - **`patterns`, not a string, is what travels down.** `matchesFilter` split/trimmed/lowercased the needle once per table per render; on a large catalogue that allocation, not the `includes`, is the dominant cost of a keystroke. It is parsed once in `commit()`, and `commit` keeps the previous array's *identity* when the needle is unchanged — which is what lets the explorers depend on it. Same move one level up: `useTreeMatchCounts` holds the app's only subscription to `useSchema.byConnection` (there used to be one per explorer), safe as a raw selector for the usual reason (the store replaces slices, never mutates them, gotcha #1), with a `WeakMap` keyed on each slice's `tables` array caching the lowercased names — a self-invalidating cache key for free.
    - **One debounce, in the box.** Each `MultiDbExplorer` had its own, and `DatabaseRoot` was handed the *raw* filter while the database list was chosen by the debounced one, so for 250 ms after each keystroke the tree filtered its contents by a different needle than the one that decided what to show. With no string travelling as a prop that state is unrepresentable. 180 ms, not 250: the old value existed to throttle pool opens, not renders.
    - **A filter's fold is visual and ephemeral.** It must never touch `useUi.collapsedConnections` — that set goes through `persistLaunchState`, so folding by search would leave permanent folds in the environment's `LaunchState` that nobody asked for. The automatic fold is component-local and evaporates with the needle; the chevron still works, as an override that lasts as long as the search.
    - **The filter never hides a connection row**, only dims and folds it: those rows are what the user needs in order to connect one or narrow the search to it.
    - `data-kb-scope="tree"` lives on `ConnectionsTree`, not `SchemaExplorer`. Declared on the explorer it covered only an *expanded* connection's subtree — the filter box and every row were outside it, i.e. the two places a `tree` binding is most likely pressed. Related: `focusTreeFilter` is scoped `global` on purpose, since a `tree`-scoped binding is only audible from inside the panel and could never be the thing that takes you there.

56. **The shared-origin editor edits a DOCUMENT, and three of its rules are the whole feature.** `src-tauri/src/origin_doc/` is the pure model (draft ⇄ file, membership, publish impact); `commands/origin_doc.rs` is the I/O around it; `src/components/origins/` is the overlay, mounted as a **sibling** of `SettingsDialog` in `App.tsx` (opening it closes Settings — never a dialog trapping focus on top of another). What will bite:
    - **Nothing in it touches this machine's state, in either direction.** An `OriginDraft` never reads or writes `profiles.json` / `tab_state.json` / `json_schemas.json`, and saving one changes nothing locally. That is what makes the merge rules testable at all — gotcha #52 is the record of what happens when the only entry point insists on saving first, and every test in `origin_doc/tests.rs` is pure for exactly that reason. The local profile list and schema library are read *only* to offer rows to copy into the document.
    - **A secret that did not change travels VERBATIM, and that is a correctness property, not an optimisation.** `encrypt_secret` draws a fresh salt and nonce per call, so re-encrypting invalidates every consumer's `landed_secrets` fingerprint cache (gotcha's neighbour: `already_landed`) and costs each of them ~600 000 PBKDF2 rounds *per slot*. `SecretSlot::Keep` carries the envelope byte for byte; the pristine draft is kept for the whole editing session precisely so leaving `keep` and coming back **restores** the envelope rather than rebuilding it, which the editor cannot do (it has neither the plaintext nor the passphrase). Renaming an environment must cost zero derivations, and `renaming_an_environment_re_encrypts_nothing` is the test that says so.
    - **`source_environment_id` is sacred** — it is the `(origin_id, origin_source_id)` identity `sync_environment_bundles` matches a bundle against its local mirror with. Minting a fresh one while editing makes every consumer see that environment *disappear* and a different one arrive, losing tabs, layout and filters. Exactly one place mints one: creating an environment that never existed. Same one level down for `ConnectionProfile.id`, which is what lets a publisher consume their own origin without ending up with two copies of every server.
    - **`publish_impact` runs the REAL `merge_into`** against a synthetic pool built from the file it is about to replace, rather than re-deriving the rules — and reads the refreshed/unchanged split off the simulated pool *after* the merge, so it needs no knowledge of which fields a refresh preserves locally (`mcp_write`, today). It computes `vanished` itself, though, and that is the point: `merge_into` **clears** `vanished` once the read crosses the suspicion threshold, so the consumer's own report can never reveal that a publish will reach nobody. `EntityImpact.silently_dropped` is the only surface in the product where that is discoverable.
    - **Three layers decide whether a write is allowed, and only the middle one is authoritative.** `Origin.role` (`#[serde(default)] = Consumer`) is *intention*, so no existing origin gains write access by updating; `probe_origin_writable` creates and deletes a real file next to the document, because permission bits on a Windows share describe the local mount and not what the server accepts; `meta.maintainer`/`meta.revision` are *coordination* and grant nothing. What actually stops two publishers clobbering each other is the SHA-256 the save re-computes from disk — a conflict comes back as `Ok(SaveOutcome::Conflict)` carrying the newer document, **not** an `Err`, because errors cross the IPC boundary as plain strings and could not carry it.
    - **`state_file::write_atomic` takes an arbitrary path; `save_atomic` does not and must not.** `save_atomic` only resolves names under the config dir, which is what keeps gotcha #26's canary isolation enforceable in one place. The temp file goes in the *destination's* directory (a `rename` is only atomic within a filesystem, and a share is another volume), is `fsync`ed before the rename, and the previous revision is copied — not moved — to `<name>.bak`.
    - **The JSON Schema slice syncs by ID, through `json_schemas::origin`, never through `json_schemas::import`.** The one-shot importer mints fresh uuids, clears `origin_id` and resolves conflicts by *name*, all correct for a file picked once and all wrong for a four-hourly poll: it would grow `cfg (2)`, `cfg (3)`, … forever, or adopt a locally-authored schema that happens to share a name. The sync path is `merge_into`'s shape instead — ownership by `origin_id`, refresh in place, a published name that collides with a local one steps aside, a binding naming an unknown connection lands `enabled: false` with its pin intact, and nothing deletes.

57. **The Mongo pipeline completion provider adopted `monacoSql.ts`'s per-model registry (gotcha #9), and its live suggestions are computed from a cursor-position scanner that is deliberately not a parser.** `src/lib/monaco/monacoMongo.ts` used to offer only three *static* suggestion families (stage operators, expression operators, BSON constructors) — no field or collection name ever appeared, because nothing connected the provider to `useSchema`. Two things had to be true before that data could be wired in without repeating past mistakes:
    - **The provider stays global to the language; a `Map<modelUri, MongoCompletionEntry>` (`registerMongoEditor`) carries the per-editor data**, exactly like `monacoSql.ts`'s `registry`/`registerSqlEditor`. Registering a second `registerCompletionItemProvider` per `PipelineEditor` instance would have reproduced gotcha #9's "N duplicate providers with N tabs open" bug for this language too — the whole reason that gotcha exists is that this is easy to get wrong a second time in a sibling file.
    - **Knowing "is the cursor inside `$lookup.from`?" needs *some* structural awareness of the stage body, but gotcha #33 still holds: the frontend never parses a pipeline.** `src/lib/mongo/completionContext.ts`'s `completionPositionAt` is a single forward scan that tracks brace/bracket depth and which key precedes each value — enough to answer "what key is this value the value of, and is that key's own value itself the value of `$lookup`?" — and nothing more: no validation, no AST, and it degrades to `"unknown"` rather than guessing on anything it doesn't recognise, same philosophy as `pipeline.ts`'s `firstKeySpan`/`operatorOf` it sits next to in spirit (different file, because pipeline.ts's own doc comment calls `firstKeySpan` "the one place" it reads a body — a second, differently-shaped scanner earned its own module rather than muddying that claim). It never looks past the cursor either: an auto-closed quote sitting after the cursor is not "closed" from the scanner's point of view, which is what keeps `$lookup.from: "|"` (cursor between the two auto-inserted quotes) reporting the right key instead of reading ahead into unwritten territory.
    - **Every suggestion source is either already in memory or fetched at most once per collection per session.** `AggregationTab` reads `useSchema.byConnection[connectionId].tables`/`.columns` — the same eager table list and lazy, session-cached `loadColumns` (`infer_columns`, top-level fields only) the schema tree already uses — and adds one `pendingFieldsRef` set on top, so a burst of completion requests for a collection whose fields haven't loaded yet (one per keystroke, since the provider can't await anything) fires `loadColumns` at most once, not once per keystroke. A `$lookup`'s `from` collection is only ever sampled once the user actually references it; the pipeline's own source collection is preloaded eagerly since it's needed almost everywhere. No backend changes were needed — `list_tables`/`list_columns` already covered both cases.
    - **Nested/dotted field paths (`customData.format`) and "fields after this stage" are out of scope on purpose.** `infer_columns` only returns top-level fields, and the live per-stage output (`AggregationTab.stagePreviews`) that *would* let a later stage suggest fields the previous stage actually produced was left unconnected — both are natural follow-ups (the latter via `lib/grid/documentTree.ts`'s `flattenDocument`, which already turns a sampled `QueryResult` row into dotted paths for the list view), not implemented here, to keep the first version's surface area — and its risk of a wrong-but-confident suggestion — small.

58. **The MCP connector's exposed set lives on the profile, its `--connections` flag has THREE states, and the name resolver had to be pure to be testable at all.** Which connections the sidecar may reach used to live only in the MCP client's own config (`--connections <uuid>,<uuid>`), which is the same misplacement gotcha #39 argues about JSON-Schema bindings, one level out: the app owned the decision and could not make it. The tell was the asymmetry — `mcp_write`, the *more* security-relevant half, was already on `ConnectionProfile` and already re-read from disk per write attempt, so the coarser knob was the nailed-down one. It is now `ConnectionProfile::mcp_exposed`, and the pieces that will bite:
    - **`Config.pinned` is `Option<HashSet<String>>`, and all three states are load-bearing.** `None` (no flag) defers to `mcp_exposed`; `Some(set)` pins that set for the life of the process, because an argument the user typed outranks a checkbox — in *both* directions, so ticking a box must not widen a pinned client and unticking must not narrow it; `Some(empty)` (`--connections ""`) is an explicit "expose nothing" and must never collapse into `None`, which would turn a deliberate lockdown into a wide-open one on upgrade. Opt-in survives the migration for free: `mcp_exposed` defaults to `false`, so a client launched bare after the upgrade reaches nothing until the user ticks something.
    - **Exposure is re-read per call, which is the whole point, and that broke the bridge's model.** The app cached the allowlist from the `Hello` frame for the session; a handshake happens once and an MCP client holds its sidecar for days, so a snapshot reproduced exactly the staleness the change removes. `bridge::server::Exposure` now has two variants — `Declared(set)` for a pinned client, `FromProfiles` for a deferring one, which re-asks `state.profiles` (in memory, and the app owns the file) per request. The `Hello` flag is additive with **no `PROTOCOL_VERSION` bump**, and the sidecar still sends its startup snapshot in `allowed` even when deferring: an old app then enforces the snapshot, which is the *old behaviour* rather than a refusal — and a refusal is the one outcome the sidecar cannot degrade from, since it arrives as an error reply mid-tool-call instead of `Unreachable` (see that constant's own doc).
    - **`resolve_connection` is a free function taking `(&Config, &str, &[ConnectionProfile])`, not a method.** It began as a method reading `self.all_profiles()`, which reads the real `profiles.json` — so every test of it would have answered differently on the maintainer's machine (31 profiles) than in CI (none), which is gotcha #52's lesson arriving one function early: a seam, not a mock. Note `write_policy` gets away with the disk read only because its fallback is per-*lookup* (`.find().or_else(in-memory)`), which a whole-list read cannot copy.
    - **An id always wins over a colliding name**, resolution is scoped to exposed profiles only (a name must not reach what the user did not expose), an ambiguous name is refused with its candidates listed rather than guessed at — profile names are not unique, and two clients' "Producción" is the ordinary case — and a real-but-unexposed reference gets its own message naming the fix that applies (a checkbox, or the command line). Every tool canonicalises in its first line via `Parameters(mut a)`; `ensure_connected` re-checks anyway, because that convention is exactly what a new tool forgets.
    - **Strictly local in both directions.** `merge_into` preserves it across a shared-origin sync (a publisher cannot expose a database here; a refresh cannot revoke access mid-session) and `apply_profile_imports` **clears** it — `ExportedProfile` flattens the whole `ConnectionProfile`, so a bundle from a machine that had it set would otherwise expose those servers the moment someone imported it to look at. `mcp_write` is deliberately left alone on import: a policy on a connection nothing can reach grants nothing.

## Workflow

```powershell
# dev (Tauri shell + Vite HMR)
pnpm tauri:dev

# production bundle (Windows .msi / Linux .deb / .AppImage)
pnpm tauri:build

# quick reality check (downloads the Chinook SQLite sample, ~1 MB)
mkdir -p sample-data
curl -L -o sample-data/chinook.db `
  https://github.com/lerocha/chinook-database/raw/master/ChinookDatabase/DataSources/Chinook_Sqlite.sqlite
# then in HuginnDB: + connection → SQLite → path to chinook.db
```

`sample-data/` is gitignored on purpose — don't commit fixtures.

First build is **slow** (5–10 min) because Cargo compiles all three `sqlx` drivers + `keyring` + `tokio` from scratch. Incremental rebuilds are <10 s.

The Rust toolchain + MSVC Build Tools (Windows) are prerequisites; the user already has both. Tauri's per-platform deps are in the README.

## Architecture invariants

- The **frontend never talks to a database directly.** All DB I/O lives in Rust commands. The frontend uses the typed wrapper at `src/lib/tauri.ts` — do not call `invoke` from components.
- **Passwords never hit disk in plaintext.** `keyring` is the only persistence path. Profile metadata (host, port, db, username, SSL toggle, driver) lives in JSON inside the platform config dir; the password is keyed by `${profile.id}::${username}` in the OS keychain.
- **CSP is `null` on purpose** because Monaco loads its workers as blobs. Workers themselves are bundled (no remote fetch), so the relaxation is narrow. Tightening CSP is on the roadmap.

## On-disk state map (platform config dir)

| File                    | Owner                              | Notes |
| ----------------------- | ---------------------------------- | ----- |
| `profiles.json`         | `src-tauri/src/store.rs`           | Connection metadata only. Passwords in OS keychain. Loading a file that exists but won't parse is a hard error on purpose (unlike every other file here) — silently substituting an empty list would show the user an app that has lost every saved connection, and the next save would make that true on disk. |
| `prefs.json`            | `src-tauri/src/prefs.rs`           | User preferences (editor / grid / ui). Atomic temp-file + rename on write. Bad JSON falls back to `Preferences::default()` — never blocks startup. |
| `tab_state.json`        | `src-tauri/src/tab_state.rs`       | **v5** — `{ version, environments[], activeEnvironmentId, origins }`; each environment owns its `connections` map (LRU-pruned to 20 *per environment*; query bodies capped at 64 KB), its dockview geometry and its `launch` state, while `origins` is a **global** registry (gotcha #40) whose entries also carry this machine's `role` for that file (`consumer` by default — gotcha #56) and the last-seen `maintainer`. Written only by the main window (see gotchas #8 and #27). v1–v4 blobs migrate: v1/v2/v3 fold into one unnamed environment (v2 "workspaces" still lose all but the active one), and v4's per-environment origins are hoisted and deduped by path. |
| `json_schemas.json`     | `src-tauri/src/json_schemas/`      | User JSON Schema library + per-column bindings. **Global**, not per environment, and never pruned (see gotcha #39). Atomic temp-file + rename; bad JSON falls back to an empty library rather than blocking startup. Bodies are stored as source text and the backend never parses them. |
| `*.window-state.json`   | `tauri-plugin-window-state` v2     | Plugin-owned; do not parse manually. Removes need for a hand-rolled `window.rs`. |
| `pulse.db`              | `src-tauri/src/pulse/store.rs`     | **The one file here that is not JSON.** Pulse's on-disk history — a SQLite database (WAL, single `samples(connection_id, ts_ms, metric, value)` table), appended to by `pulse::sampler`'s 60 s tick rather than rewritten whole like every file above it; `state_file::save_atomic`'s whole-blob-atomic-rename pattern is exactly the write amplification a time series needs to avoid. `state_file::path("pulse.db")` still resolves *where* it lives — that function only resolves a path and creates the parent directory, it never assumes JSON — so canary isolation (gotcha #26) applies here for free. Opened lazily (first sampler tick or first Retrospectiva read), so an install where nobody has enabled Pulse on any connection never creates the file. Retention is a staircase: 60 s resolution for 48 h, downsampled to one point per 5 min out to `PulsePrefs::retention_days` (30 by default), then deleted; a `maxDiskMb` soft cap sheds the oldest tenth of what remains if the file is still over budget after that. Sampling itself is opt-in per connection (`ConnectionProfile::pulse_enabled`, off by default, preserved across a shared-origin sync the same way `mcp_write` is) and reads only what `pulse::sampler` needs in one round trip — `db::mysql::pulse::sample`/`db::mongo::pulse::sample`, not the two-round-trip `health()` the live panel uses. |

Theme + dockview layout still live in `localStorage` (keys `huginndb.theme.v2` and `huginndb.layout`) — synchronous read pre-mount avoids FOUC. Don't migrate these to disk without a plan for the flash.

## When the user asks for "the next thing"

- Default to the **top open item in `ROADMAP.md`** unless they say otherwise.
- Always ask before adding new dependencies; the user prefers a small, audited tree.
- Keep PRs / commits scoped. The user values legible history and will read the long-form commit body.

## Communication style

- Replies in Spanish, terse, no fluff. The user reads diffs and runs commands themselves; they don't need a walkthrough.
- One sentence before a tool batch is enough.
- End-of-turn summary: ≤ 2 sentences. What landed, what's next.
- When proposing a non-trivial change, ask 1–2 scoping questions with `AskUserQuestion` rather than guessing.
